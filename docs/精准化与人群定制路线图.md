## 2. P-TAG-01 场景标签 + 标签专题区

### 2.1 产品动机

当前 `interestTags` 12 个 slug（culture/nature/food/family 等）偏「景点类型」，无法表达「溜娃、约会、玩水、纳凉、避暑、赏花、夜游」这类**场景动机**。用户搜索时更习惯按场景而非类型。

### 2.2 方案

**双层标签体系**：

| 层 | 字段 | 取值 | 落点 |
|----|------|------|------|
| 类型层（已有） | `attractions.tags` / `users.interestTags` | culture/nature/food… | 不动 |
| 场景层（新增） | `attractions.sceneTags` | `溜娃/约会/玩水/纳凉/赏花/夜游/避暑/踏青/祈福/露营` | 新增 json 字段 |

**专题区**：

- 首页/广场新增「场景专题」入口（横向 chip 行）：点击进入 `/scenes/:slug` 专题页
- 专题页聚合：该场景的景点卡片 + 该场景的路线 + 该场景的标品（M5）+ 该场景的单景点需求（P-DEMAND-01）
- 路线表 `travel_routes` 新增 `sceneTags` json，规划生成时由 LLM 从 prompt 抽取并写入

### 2.3 数据模型变更

```ts
// attractions 新增
sceneTags: json('scene_tags').$type<string[]>(),

// travel_routes 新增
sceneTags: json('scene_tags').$type<string[]>(),

// users 新增（用户偏好场景，用于首页推荐）
preferredScenes: json('preferred_scenes').$type<string[]>(),
```

### 2.4 i18n

新增 `shared/src/i18n/scene-tags.ts`，结构对齐 `interest-tags.ts`：zh-CN 存中文值，en-US 展示 `Family fun / Date / Water play / Cool retreat …`。

## 3. P-LIVE-01 景点打卡实时人数

### 3.1 产品动机

用户决策「现在去不去」时，最关心**当前人多不多**。纯展示「历史打卡数」不够实时。

### 3.2 方案

**数据源**（三档，按可用性降级）：

1. **打卡计数**（自有）：当日 `check_ins` 中 `attractionId=X` 且 `checkedAt` 在最近 N 小时的去重用户数
2. **估算系数**：`当日打卡数 × 估算系数`（默认 30，可按城市/景点热度配置），冷启动期主要展示「稀疏/适中/密集」三档语义
3. **第三方实时 API**（远期）：高德/百度人流 API 或景区官方开放数据

**缓存**：Redis key `live:attraction:{id}:count`，TTL 5 分钟；写入打卡时增量更新。

**隐私与展示**：

- 当计数 < 阈值（默认 5）时，展示「人少」而非具体数字，避免暴露个体行踪
- 仅展示「稀疏 / 适中 / 密集 / 旺季」四档语义 + 趋势箭头（↑↓→）
- 详情页 + 专题页 + 单景点需求列表均可见

### 3.3 数据模型

```ts
// 新增 attraction_live_stats 视图（不落表，按 check_ins 聚合 + Redis 缓存）
// 或 attractions 新增冗余字段（每小时跑批刷新）
liveVisitorLevel: tinyint('live_visitor_level'),  // 0~3
liveVisitorUpdatedAt: timestamp('live_visitor_updated_at'),
```

### 3.4 验收

- [ ] 景点详情/专题页显示实时人数档位
- [ ] 打卡后 5 分钟内档位可感知更新
- [ ] 计数 < 5 时不暴露具体数字
- [ ] `p-live:visitor-count-cases` 全绿

## 6. P-MEMORY-01 已去景点避重推荐

### 6.1 产品动机

用户多次规划后常抱怨「又推荐我去过的景点」。`user_travel_persona.avoidList` 已有字段但未注入规划。

### 6.2 方案

**数据来源**：

- `check_ins.attractionId`（已打过卡的）
- `travel_routes.routeDetail.days[].attractions[].attractionId`（已规划过的）
- `pet_memories` 中 `type=regret` 的 POI（明确不想再去的）

**注入点**：

1. **C2 意图解析**：`TravelIntentSnapshot` 新增 `visitedAttractionIds: number[]` + `avoidAttractionIds: number[]`
2. **C3 RAG 检索**：检索时 `WHERE id NOT IN (visitedIds)`（可配置软过滤：降权而非硬过滤）
3. **LLM Prompt**：注入「用户已去过：[景点名列表]，请优先推荐新景点」
4. **Enricher**：生成后对 POI 列表做去重校验，命中已去过则写 `warnings[]`

**用户可控**：

- 个人中心新增「记忆与避重」开关：
  - 严格避重（默认）：已去过不再出现
  - 软避重：降权但仍可出现
  - 关闭：不参考历史
- 可手动「标记不想再去」/「标记可重复去」

### 6.3 验收

- [ ] 规划时注入已去过 POI 列表
- [ ] 默认严格避重，已去过景点不再推荐
- [ ] 用户可切换避重策略
- [ ] `p-memory:avoid-repeat-cases` 全绿

## 8. P-INPUT-01 规划对话标签化定制

### 8.1 产品动机

当前规划页（mobile `pages/plan/plan.vue` · pc `views/PlanView.vue`）依赖**纯文本输入**，用户需自己组织「带 2 个孩子去杭州玩 3 天预算 5000 想玩水纳凉」这样的描述。门槛高：

- 不熟悉旅行术语的用户不知如何描述
- 关键约束（天数/预算/人数/场景）容易遗漏，导致 LLM 反复追问
- 文本输入在移动端体验差，尤其单手场景

**目标**：在保留对话式输入的前提下，新增**标签化定制面板**，让用户通过点选标签/滑块/选择器直接构建 `TravelIntentSnapshot`，无需打字即可发起规划。

### 8.2 方案

**双轨输入**（不替代对话，作为补充）：

```text
规划页
  ├─ 对话输入区（现有，保留）
  └─ 标签定制面板（新增，可折叠/展开）
       ├─ 目的地：城市多选 chip（来自 attractions.cities + 热门城市）
       ├─ 天数：滑块或 chip（1/2/3/5/7/自定义）
       ├─ 预算：档位 chip（经济 <2k / 舒适 2-5k / 品质 5-10k / 奢华 >10k）+ 自定义区间
       ├─ 游玩属性：类型标签 chip（复用 interestTags 12 个 slug）
       ├─ 场景标签 chip（复用 P-TAG-01 sceneTags：溜娃/约会/玩水/纳凉…）
       ├─ 人数与同伴结构：人数 stepper + 同伴 chip（独行/情侣/家庭/团体）
       ├─ 大交通偏好：高铁/飞机/自驾/不限（H9 transportPreference）
       ├─ 住宿档次：经济/舒适/豪华/不限（H9 lodgingTier）
       ├─ 出发日期：日期选择器（H9-3 startDate）
       └─ 一键生成 → 直接构建 TravelIntentSnapshot 调 /routes/generate
```

**与 C2 意图解析的关系**：

- 用户点选标签后，前端直接构建 `TravelIntentSnapshot`（`source='manual'`），跳过 LLM 意图解析步骤
- 仍可叠加文本输入：文本会与已选标签合并，C2 解析时以已选标签为强约束
- `TravelIntentSnapshot` 新增 `source` 字段：`'rule' | 'llm' | 'hybrid' | 'manual'`

**与 C7 Agent 的关系**：

- 标签化输入是 Agent 的「快捷指令」：用户无需用自然语言描述意图，直接给 Agent 一个结构化起点
- Agent 追问时，标签面板可高亮「待补充字段」（如已选城市但未选天数，天数 chip 闪烁提示）

### 8.3 数据模型变更

```ts
// TravelIntentSnapshot 新增
source?: 'rule' | 'llm' | 'hybrid' | 'manual';
companionStructure?: string[];  // solo / couple / family / group（与 user_travel_persona 对齐）
headcount?: number;             // 人数
```

### 8.4 UI 规范

- 移动端：标签面板默认折叠为「快速定制」按钮，展开后底部抽屉式弹出（参考 `VoiceTextComposer` 交互）
- PC：标签面板作为对话区右侧常驻侧栏（双栏布局已有，复用 `PlanView` 右栏）
- 标签 chip 复用 `DouxingEmptyState` 同款 token，不硬编码颜色

## 9. P-ONBOARD-01 首次进入标签引导 + 分类标签体系

### 9.1 产品动机

当前注册后直接进首页，`interestTags` 为空，导致：

- 首页推荐无个性化，新用户看到的内容与老用户一致
- 规划时 C2 意图解析缺用户偏好上下文，需反复追问
- `user_travel_persona` 画像冷启动慢，需多次打卡/规划后才有数据

**目标**：注册后首次进入时，通过**轻量分类标签引导**快速建立用户画像，让首页推荐与规划体验**从第一次就精准**。

### 9.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **可跳过** | 任何步骤均可「跳过」，避免选择困难与流失 |
| **默认非空** | 跳过时系统按热门默认填充，保证画像字段非空 |
| **分类选择** | 每步只在一个大类里选小类，降低认知负荷 |
| **可修改** | 个人信息页展示已选标签，随时可改 |
| **渐进收集** | 引导只收核心三类；补充类后续在规划/打卡中渐进收集 |

### 9.3 标签分类体系

**三大核心类**（引导必经，可跳过则默认）：

#### 类一：基础属性（who）

| 小类 | 取值 | 默认（跳过时） | 备注 |
|------|------|----------------|------|
| 性别 | 男 / 女 / 其他 / 不愿透露 | 不愿透露 | 自愿；与 P-PROFILE-01 `gender` 字段对齐 |
| 年龄段 | 18-22 大学生 / 23-30 职场新人 / 31-40 成家期 / 41-50 中年 / 50+ 银发 | 23-30（最活跃） | 不收集精确年龄，仅年龄段；与 P-PROFILE-01 `birthYear` 推算对齐 |

#### 类二：旅行半径（where）

| 小类 | 取值 | 默认（跳过时） | 备注 |
|------|------|----------------|------|
| 旅行半径 | 城市周边（周末微度假）/ 国内长途 / 全球旅行 / 都喜欢 | 都喜欢 | 决定推荐景点的地理范围；与 `attractions.city` 筛选对齐 |

#### 类三：旅行场景（why）

复用 P-TAG-01 `sceneTags`，引导时展示热门子集：

| 小类 | 取值（热门子集） | 默认（跳过时） | 备注 |
|------|------------------|----------------|------|
| 旅行场景 | 溜娃 / 约会 / 玩水 / 纳凉 / 赏花 / 夜游 / 避暑 / 露营 / 独行放松 / 团建 | 溜娃 + 纳凉（夏季热门） | 多选；与 P-TAG-01 `sceneTags` 同源；完整列表在专题页 |

**可选补充类**（引导中可选「更多」展开，或后续渐进收集）：

| 类 | 小类 | 取值 | 与现有字段对齐 |
|----|------|------|----------------|
| 兴趣类型 | 文化/自然/美食/亲子/娱乐/都市/购物/夜景/历史/休闲/户外/摄影 | 12 个 `interestTags` slug | 现有 `users.interestTags` |
| 同伴结构 | 独行 / 情侣 / 家庭 / 团体 | 与 P-INPUT-01 `companionStructure` 对齐 | 新增 `users.companionStructure` |
| 预算档次 | 经济 / 舒适 / 品质 / 奢华 | 与 H9 `lodgingTier` + P-INPUT-01 预算档对齐 | 新增 `users.budgetTier` |
| 出行节奏 | 轻松 / 适中 / 紧凑 | 与 `user_travel_persona.rhythm` 对齐 | 渐进收集，不进引导 |

### 9.4 引导流程

```text
注册成功
  ↓
首次进入首页前
  ↓
[Step 1/3] 你是？→ 性别 chip + 年龄段 chip（可跳过）
  ↓
[Step 2/3] 想去多远？→ 旅行半径 chip（可跳过）
  ↓
[Step 3/3] 喜欢怎么玩？→ 旅行场景 chip 多选（可跳过）
  ↓
[可选] 更多偏好？→ 展开兴趣类型 / 同伴 / 预算（默认折叠）
  ↓
完成 → 写入 users 字段 + 触发 user_travel_persona 首次生成
  ↓
进入首页（推荐已个性化）
```

**交互细节**：

- 每步顶部显示「3 步快速定制你的旅行 / Step 1 of 3」+ 跳过按钮
- chip 选中态用 `--dx-primary` token，不硬编码颜色
- 跳过时该类用默认值填充（保证非空），并在完成页提示「已为你选中默认偏好，可随时在个人中心修改」
- 完成页可一键回看所有已选标签并修改

### 9.8 精准化人群定制化旅游景点推荐方案

#### 9.8.1 推荐架构

```text
用户画像（引导 + 行为沉淀）
  │
  ├─ 基础属性：gender + ageRange
  ├─ 旅行半径：travelRadius
  ├─ 旅行场景：preferredScenes
  ├─ 兴趣类型：interestTags
  ├─ 同伴结构：companionStructure
  ├─ 预算档次：budgetTier
  └─ 行为沉淀：check_ins / travel_routes / pet_memories → user_travel_persona
  ↓
推荐引擎（多路召回 + 加权排序）
  ├─ 召回路 1：场景匹配（attractions.sceneTags ∩ preferredScenes）
  ├─ 召回路 2：兴趣匹配（attractions.tags ∩ interestTags）
  ├─ 召回路 3：人群热门（同 ageRange+gender 的高频打卡景点）
  ├─ 召回路 4：地理半径（travelRadius 过滤）
  ├─ 召回路 5：避重过滤（P-MEMORY-01，排除已去过）
  └─ 召回路 6：同伴适配（family → 亲子友好景点，couple → 约会场景）
  ↓
加权排序（综合分）
  score = w1·场景匹配 + w2·兴趣匹配 + w3·人群热度 + w4·距离 + w5·预算适配 - w6·已去过惩罚
  ↓
推荐结果（首页 / 专题页 / 规划注入）
```

#### 9.8.2 人群定制化推荐示例

| 人群画像 | 召回偏好 | 推荐示例 |
|----------|----------|----------|
| 23-30 女 + 约会 + 城市周边 + 舒适预算 | 约会场景 + 都市类型 + 同城 + 中档 | 城市观景餐厅、夜景酒吧、艺术街区、情侣 SPA |
| 31-40 男 + 溜娃 + 国内长途 + 经济预算 | 亲子场景 + 自然/娱乐类型 + 亲子友好 | 主题乐园、自然公园、亲子农场、博物馆 |
| 50+ 不限 + 纳凉 + 国内长途 + 品质预算 | 纳凉场景 + 自然/休闲类型 + 高分景点 | 山地避暑、温泉度假、湖泊游船、园林 |
| 18-22 女 + 玩水 + 城市周边 + 经济预算 | 玩水场景 + 娱乐/户外类型 + 同城低价 | 水上乐园、漂流、海滩、城市泳池派对 |
| 23-30 男 + 露营 + 全球旅行 + 品质预算 | 露营场景 + 户外类型 + 高分 + 远距离 | 国家公园、野外露营地、徒步线路、星空营地 |

#### 9.8.3 实现方案

**Phase 1（MVP，随 P-ONBOARD-01 落地）**：

- 后端 `recommendation.service.ts`：单路召回（场景匹配 + 兴趣匹配 + 半径过滤）

### 13.2 意图解析层（C2）优化

**优化点 1：标签直接构建意图，跳过 LLM 解析**

P-INPUT-01 标签化定制后，前端直接构建 `TravelIntentSnapshot`（`source='manual'`），跳过 C2 LLM 解析，节省一次 LLM 调用与延迟。

**优化点 2：标签 + 文本混合时的强约束合并**

```
finalIntent = {
  ...tagIntent,                    // 标签构建的强约束
  ...parsedTextIntent,              // 文本解析的补充（不覆盖标签）
  source: 'hybrid'
}
```

**优化点 3：C2 新增 `sceneTags` 解析**

C2 从文本抽取场景标签（如「带娃玩水」→ `sceneTags: ['溜娃', '玩水']`），与 `themes` 并列注入下游。纯文本输入的用户也能享受场景标签精准化。

### 13.3 RAG 检索层（C3）优化

**优化点 4：RAG topK 重排引入场景匹配分**

```
ragScore = w1·热度 + w2·类型匹配 + w3·场景匹配(sceneTags ∩ preferredScenes) + w4·人群热度
```

同样检索「杭州」，溜娃用户优先看到亲子乐园，约会用户优先看到观景餐厅。

**优化点 5：避重过滤前置到 RAG**

避重过滤前置到 RAG 检索阶段（`WHERE id NOT IN (visitedIds)`），避免已去过景点进入候选池，减少后续 LLM 处理量。

**优化点 6：RAG 参数按人群画像动态调整**

| 人群 | topK | variants | 理由 |
|------|------|----------|------|
| 通用 | 20 | 3 | 现状 |
| 溜娃家庭 | 30 | 3 | 亲子景点需更多候选 |
| 银发 | 15 | 2 | 偏好精选少选 |
| 探索型 | 40 | 4 | 喜欢多样选择 |

### 13.4 Prompt 层优化

**优化点 7：Prompt 注入「人群画像段」+「场景标签」+「已去过列表」**

```
【人群画像】23-30 岁女性，偏好约会场景，城市周边，舒适预算，情侣出行
【场景标签】溜娃、玩水
【已去过景点】西湖、灵隐寺、雷峰塔（请避免重复推荐）
【同伴结构】couple，2 人
```

**优化点 8：按场景标签分支 Prompt 模板库**

| 场景 | Prompt 模板特点 |
|------|-----------------|
| 溜娃 | 强调亲子友好、安全、休息点、避免长途 |
| 约会 | 强调浪漫氛围、拍照点、夜景、餐厅 |
| 玩水 | 强调水上项目、安全、更衣设施 |
| 纳凉 | 强调海拔、树荫、避暑胜地 |
| 露营 | 强调营地、装备、星空、安全 |

模板库由运营维护（Web CRUD），类似 H9+-2 playbook CRUD。

### 13.5 Agent 层（C7）优化

**优化点 9：新增「标签调整」意图路由**

```
「换个场景，改成约会」  → tweak_tags → 更新 intentSnapshot.sceneTags → 重新规划
「加个玩水标签」        → tweak_tags → 增量更新 → patch 而非重生
```

**优化点 10：Agent 主动读取画像建议**

```
「你之前选了溜娃场景，要不要带孩子去 XX 主题乐园？」
「你同龄人最近都在去 XX，要不要加入行程？」
「你已去过西湖，要不要换成湘湖？」
```

Agent 从「被动应答」升级为「主动顾问」。

### 13.6 Enricher 层（H9）优化

**优化点 11：段间交通选型参考场景标签**

| 场景 | 段间偏好 |
|------|----------|
| 溜娃 | 优先步行/观光车，避免长途自驾 |
| 约会 | 优先出租车/网约车，避免挤公交 |
| 露营 | 优先自驾，携带装备 |
| 银发 | 优先出租车，避免步行过长 |

**优化点 12：住宿选址参考同伴结构**

| 同伴 | 住宿偏好 |
|------|----------|
| family | 优先家庭房/亲子酒店/有儿童设施 |
| couple | 优先景观房/浪漫主题 |
| solo | 优先青旅/经济型 |
| group | 优先多床位/套房 |

### 13.7 流程编排层（C7-W）优化

**优化点 13：工作流模板按场景标签分支**

```
workflowTemplate = selectTemplate(intent, sceneTags)
  - plan_new + 溜娃   → family_fun_workflow
  - plan_new + 约会   → romantic_workflow
  - plan_new + 露营   → camping_workflow
  - tweak_day + 任意  → patch_workflow
```

不同场景走不同的 RAG topK / Enricher 参数 / Prompt 模板组合。

### 13.8 多方案生成层（C4）优化

**优化点 14：候选方案按场景标签差异化**

| 场景 | 候选 A | 候选 B | 候选 C |
|------|--------|--------|--------|
| 溜娃 | 主题乐园线 | 自然亲子线 | 博物馆线 |
| 约会 | 观景餐厅线 | 艺术街区线 | 夜景酒吧线 |
| 露营 | 野外营地线 | 星空营地线 | 徒步线路 |

用户选择时差异度明显，不会出现「三套都差不多」。

### 13.9 行中智能层（H7/H8）优化

**优化点 15：重规划替补参考场景标签**

```
错过景点 = 亲子乐园（溜娃场景）
替补候选 = WHERE sceneTags ∩ ['溜娃'] AND NOT IN (visitedIds)
```

溜娃场景错过景点后，替补仍是亲子友好，不会推荐深夜酒吧。

**优化点 16：行中异常救场结合画像**

| 人群 | 疲劳救场建议 |
|------|--------------|
| 带娃家庭 | 建议回酒店休息，推荐附近亲子餐厅 |
| 情侣 | 建议改去咖啡馆/甜品店 |
| 银发 | 建议缩短行程，优先休息 |

### 13.10 反馈环与训练数据优化

**优化点 17：Golden Case 按人群画像分桶**

```
recallGoldenCase(currentPersona) = 
  SELECT * FROM golden_cases 
  WHERE age_range = currentPersona.ageRange 
    AND scene_tags ∩ currentPersona.preferredScenes
  LIMIT 5
```

23-30 女性规划时召回同人群案例，而非 50+ 银发案例。

**优化点 18：I1/I3 训练数据分层采样**

训练数据生成时按人群画像分层采样，确保各人群都有足够样本：

```
trainingData = [
  ...generateSamples(persona='23-30 female, 约会'),
  ...generateSamples(persona='31-40 male, 溜娃'),
  ...generateSamples(persona='50+ , 纳凉'),
  ...
]
```

专属模型对各类人群生成质量均衡，不偏袒主流人群。

### 13.11 记忆与画像联动优化

**优化点 19：画像刷新纳入场景标签偏好**

用户多次规划「溜娃」场景 → 画像 `preferredScenes` 权重自动提升「溜娃」；多次跳过「约会」场景 → 权重下降。画像从「引导填写」进化为「行为沉淀」。

**优化点 20：记忆召回按场景标签过滤**

```
recallMemory(currentScene='溜娃') = 
  WHERE memory.sceneTags ∩ ['溜娃'] 
  OR memory.type = 'regret'  // regret 记忆始终召回
```

规划溜娃行程时不会被「上次约会踩坑」的记忆干扰。

### 13.12 降级链优化

**优化点 21：标签约束在降级链各层保留**

标签约束（场景标签 + 避重 + 人群画像）作为贯穿降级链的强约束，即使降级到模板，也按场景标签选模板：

```
降级到模板时：
  template = selectTemplate(sceneTags)  // 溜娃场景选亲子模板
  avoidList = visitedAttractionIds       // 避重始终生效
```

降级不降质，标签精准化在所有路径都生效。
