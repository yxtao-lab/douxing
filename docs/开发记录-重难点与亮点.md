## M0-7 手机验证码登录 + 腾讯云短信

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-20 |
| **路线图** | M0-7 |
| **关联代码** | `packages/server/src/services/sms.service.ts`、`config/sms.ts`、`routes/auth.ts`；Web/移动端登录页 |

### 背景与目标

MVP 需要手机号即可登录，且生产环境能发真实短信。设计文档要求验证码登录，但不宜在第一阶段接入多套云厂商。

### 思考过程

1. **登录与注册是否要两个接口？** 体验上用户只想「输手机号 → 收码 → 进 App」。若强行区分注册/登录，会增加表单与文案分支；验证码通过后查 `users.phone` 即可分流建号或发 Token。  
2. **短信 SDK 选型**：先在阿里云与腾讯云之间评估。阿里云 Node SDK 在 `NodeNext` + ESM 下出现 default export 无法 `new` 的问题，修 SDK 成本高；产品侧也更倾向腾讯云，故统一 `tencentcloud-sdk-nodejs`。  
3. **验证码存哪？** 首版无 Redis，用进程内 `Map` + TTL 最快可演示；接受多实例不一致，在路线图 G1 再迁 Redis。  
4. **开发环境没密钥怎么办？** `SMS_PROVIDER=mock` 时在响应/控制台给出 `devCode`，避免阻塞前后端联调。

### 最终方案

- API：`POST /auth/sms/send`、`POST /auth/sms/login`；校验通过后无用户则 `u_{phone}` 自动注册。  
- `config/sms.ts`：`auto | tencent | mock`，配置齐全走腾讯云，否则 mock。  
- 限流：60s 发送冷却、5 分钟 TTL、单码最多校验 5 次。  
- 模板参数用 `TemplateParamSet: [code]`（腾讯云 `{1}` 占位顺序）。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **登录注册合一** | 一套接口 + 一个按钮覆盖新/老用户，前端无「注册/登录」分叉。 |
| 2 | **短信渠道可插拔** | `SMS_PROVIDER` 切换腾讯云与 mock，开发不依赖真实计费短信。 |
| 3 | **失败可观测** | mock 模式返回 `devCode`，联调时不必反复查库或日志猜验证码。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **ESM 与云 SDK 兼容** | 阿里云 v4 构造器在 `NodeNext` 下不可用；改为腾讯云 SDK，并在 `package.json` 保持 `"type": "module"` 一致。 |
| 2 | **腾讯云模板参数顺序** | 占位符是 `{1}`、`{2}` 而非命名参数；用数组传参，可选 `TENCENT_SMS_TEMPLATE_MINUTES` 作为第二参数。 |
| 3 | **验证码存储与多实例** | 首版进程内 `Map` 实现简单，但多 Pod 会不一致；文档标明生产需 G1 Redis，避免误以为当前方案可原样上线。 |

## A1 用户资料与偏好

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-20 |
| **路线图** | A1 |
| **关联代码** | `routes/users.ts`、`services/user.service.ts`；`packages/mobile/src/pages/profile/edit.vue`；迁移 `0003_user_interest_tags.sql` |

### 背景与目标

验证码登录后用户只有手机号，无法支撑个性化路线推荐。需要可编辑昵称、头像、兴趣标签，并在移动端「我的」入口完成闭环。

### 思考过程

1. **头像是否等 OSS？** G2 对象存储未做，若阻塞 A1 会拖慢整阶段。折中：本地上传至 `uploads/avatars`，用 `API_PUBLIC_BASE_URL` 拼公开 URL，接口形状与未来 OSS 一致。  
2. **兴趣标签自由输入还是预设？** 完全自由会导致推荐与统计口径混乱；采用 `USER_INTEREST_PRESETS` + 最多 8 个，服务端校验，前端只做选择器。  
3. **资料接口粒度**：`GET/PUT /users/me` 与 `POST /users/me/avatar` 分离，避免 multipart 与 JSON 混在一个 PUT 里增加客户端复杂度。

### 最终方案

- `users.interest_tags` JSON 列；`PUT /users/me` 更新昵称、邮箱、标签；头像单独 multipart 上传。  
- 共享常量 `USER_INTEREST_PRESETS`、`USER_INTEREST_MAX` 同步到 `@douxing/shared`。  
- 移动端 `profile/edit.vue` 拉取/提交资料，与 Tab「我的」联动。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **先本地存储、后 OSS 演进** | 头像 URL 模型不变，后续 G2 只换存储实现，不改客户端契约。 |
| 2 | **标签预设 + 服务端校验** | 保证推荐与路线 `interestTags` 口径一致，避免脏标签进入库。 |
| 3 | **类型全仓共享** | `UpdateUserProfileRequest`、`UserInfo.interestTags` 在 shared 包，Web/移动/服务端同一套类型。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **`.env` 与公开 URL** | 头像外链依赖 `API_PUBLIC_BASE_URL`；未配置时回退 `req.protocol + host`，小程序真机需显式配局域网或域名。 |
| 2 | **multipart 与鉴权顺序** | 先 `authMiddleware` 再 `multer`，文件名带 `userId-timestamp` 防覆盖；限制 2MB 与图片 MIME。 |
| 3 | **迁移与旧库** | 新列 `interest_tags` 必须 `db:migrate`；已有用户默认为 `NULL`，前端展示为空数组而非报错。 |

## A2 景点/内容基础库

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-20 |
| **路线图** | A2 |
| **关联代码** | `schema/attractions.ts`、`data/attraction-seeds.ts`、`services/attraction.service.ts`、`routes/attractions.ts`；迁移 `0004_attractions.sql` |

### 背景与目标

路线与打卡长期不能只靠字符串景点名。需要主数据表（城市、坐标、标签），并让 `route_detail` 能挂上 `attractionId`，为 RAG、地图打卡铺路。

### 思考过程

1. **表结构先做多少？** 首版不做全文检索、不做向量；`attractions` + 索引（city、name）即可支撑列表 API 与关联。  
2. **匹配发生在什么时候？** 放在路线写入前做一次 enrich，比打卡时再猜名字更稳；打卡直接带 ID。  
3. **种子数据从哪来？** 与 `route-templates.ts` 中景点名对齐，人工补坐标与别名，保证演示路线高匹配率。

### 最终方案

- `attractions` 表 + 28 条种子（杭沪京蓉等）。  
- `GET /api/attractions`、`/cities`、`/:id`。  
- `enrichRouteDetailWithAttractionIds`：按城市 + 名称/别名/包含匹配写回 `attractionId`。  
- `check_ins.attraction_id` 可空外键。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **路线与主数据联动** | 生成/种子路线后节点带 `attractionId`，打卡、成就可复用同一 ID。 |
| 2 | **种子与模板对齐** | 模板里出现的景点名在库里都有对应行，演示时匹配率接近 100%。 |
| 3 | **别名体系** | `aliases` JSON 解决「断桥 / 断桥残雪」等叫法差异，减少重复建点。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **名称不完全一致** | 三层匹配：精确名 → 精确别名 → 包含；包含匹配在 A2+ 中降权，避免误合并。 |
| 2 | **仅关联、不扩充** | A2 初版未写入新景点，库外景点仍无 ID；推动 A2+ 做 AI 同步。 |
| 3 | **旧路线不自动修复** | seed 对已有 `travel_routes` skip；旧数据需重新生成或 `db:reset` 才带 ID。 |

## A2+ AI 景点同步（pending + 合并）

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-20 |
| **路线图** | A2 增强（路线图 §2.4 记为 A2+） |
| **关联代码** | `services/attraction-sync.service.ts`、`0005_attraction_sync_meta.sql`；`routes/attractions.ts` 审核接口 |

### 背景与目标

A2 只读匹配导致库增长慢、LLM 新景点无 ID。目标：路线生成后**反哺景点库**，但不用 AI 幻觉数据覆盖人工种子。

### 思考过程

1. **全量覆盖行不行？** 不行。LLM 的 `cost` 是估算，坐标常缺失，覆盖种子会破坏信任。应分 **来源（source）** 与 **状态（pending/active）**。  
2. **何时合并、何时新建？** 需要置信度：精确 1.0 / 别名 0.95 才合并；模糊 0.72 只关联风险大，改为新建 `pending`。阈值取 `0.85`。  
3. **pending 用户能用吗？** 生成路线的人需要 `attractionId` 打卡；公开列表只展示 `ACTIVE`，待审数据不污染搜索。  
4. **票价什么叫「最新」？** 仅 `llm_estimate` 且在价为空或超过 90 天可更新；`seed/manual` 永不因 AI 改价。

### 最终方案

- `syncAttractionsFromRouteDetail` 替代纯 enrich：匹配则 `merge`，否则 `INSERT pending`。  
- 字段：`source`、`price_source`、`match_confidence`、`verified_at` 等；坐标可空。  
- 管理端：`GET /attractions/admin/pending`、`POST .../approve` 转 `ACTIVE`。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **生成即入库** | 每次规划自动扩充库，匹配率随使用次数上升。 |
| 2 | **分来源合并策略** | 信任数据（seed/manual）防覆盖；llm 行可渐进补全。 |
| 3 | **待审与公开隔离** | 用户侧路线/打卡可用 pending ID；C 端景点列表只见已审核。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **模糊匹配误合并** | 低于 0.85 不合并，新建 pending；精确/别名才更新已有行。 |
| 2 | **AI 无可靠坐标** | pending 允许 `latitude/longitude` 为 NULL；B2 围栏前需地图 API 或人工审核补全。 |
| 3 | **票价不可当真理** | `price_source=llm_estimate` 明示参考价；禁止覆盖 seed 票价，避免误导购票。 |

| 2 | **失败自动降级** | 无 Redis 时仍可调高德。 |
| 3 | **Docker 一键起** | compose 已含 `redis` 服务与数据卷。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **ESM 引 ioredis** | 使用 `import { Redis } from 'ioredis'`，避免 default 构造报错。 |
| 2 | **只缓存成功结果** | 失败不写入，避免错误坐标长期生效。 |
| 3 | **多实例共享** | 生产多 Pod 共用同一 Redis 才能真正省配额。 |

## 数据库生成与使用命令（Drizzle）

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-20 |
| **路线图** | 横切基础设施（M0 起积累，A2/A2+ 迁移实践沉淀） |
| **关联代码** | `packages/server/drizzle/`、`src/db/migrate.ts`、`seed.ts`、`drizzle.config.ts`；根脚本 `db:*` |

### 背景与目标

Monorepo 多人协作需要可版本化的表结构变更；新人 clone 后一条命令能起 MySQL + 表 + 演示数据。

### 思考过程

1. **为什么不用手工改表？** 无法 Code Review、环境不一致；Drizzle schema 即文档，SQL 迁移可审计。  
2. **`generate` 和 `migrate` 为何常混淆？** kit 只 diff 产出文件；真正执行 DDL 的是 `migrate.ts` + `__drizzle_migrations`。必须在文档里画清流水线。  
3. **Docker 与脚本竞态** | `bootstrap` 起容器后宿主机端口未必立刻可用；`waitForDatabase` 轮询后再 `db:setup`。  
4. **seed 边界** | seed 只做 DML 且幂等 skip，不能代替 migrate；否则新人以为「跑 seed 就能加列」。

### 最终方案

- 三层：schema TS → `pnpm db:generate` → `pnpm db:migrate`；数据：`pnpm db:seed`。  
- 根目录转发 `db:migrate` / `db:seed` / `db:setup` / `db:reset`。  
- `bootstrap:dev` = Docker + wait + `db:setup` + `pnpm dev`。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **Monorepo 根命令转发** | 根目录即可 `pnpm db:migrate`，不必记住 server 包路径。 |
| 2 | **自动建库 + 等待** | `ensureDatabase` 创建库并等待 TCP 就绪，降低 Docker 新人失败率。 |
| 3 | **单一 `DATABASE_URL`** | drizzle-kit、migrate、seed、运行时共用 `.env`，减少配错连接串。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **generate ≠ migrate** | 改 schema 后必须 generate + 人工审 SQL + migrate；漏 migrate 表现为「表不存在」。 |
| 2 | **journal 不可乱改** | 已执行 tag 记在 `__drizzle_migrations`；调整历史顺序会导致环境漂移。 |
| 3 | **seed 不改表结构** | 新列/新表只能走迁移；旧业务数据不会因 seed 自动补新字段（如 `attractionId`）。 |

## A3-1 AI 路线重新生成（prompt + 景点同步）

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-20 |
| **路线图** | A3 路线能力补全（增强） |
| **关联代码** | `routes/routes.ts`（`POST /:id/regenerate`）、`services/route.service.ts`；`utils/route-detail.util.ts`；`pages/routes/detail.vue`；`packages/shared` 类型 `sourcePrompt` / `RegenerateRouteRequest` |

### 背景与目标

用户对 AI 首次生成不满意时，应能**改 prompt 覆盖草稿**而非只能新建路线；重新生成后新 POI 须与首次生成一样写入 `attractions`（pending/合并），并写回 `attractionId`。

### 思考过程

1. **新建还是原地更新？** 原地更新同一条草稿可保留订单/收藏关联（若有），且列表不膨胀；仅 `DRAFT` 可覆盖，已发布路线拒绝 regenerate 并提示去规划页新建。  
2. **旧 `attractionId` 要不要保留？** 行程节点已变，保留旧 ID 会指向错误 POI；重新生成时**剥离节点上的 `attractionId`**，强制走完整 `syncAttractionsFromRouteDetail`。  
3. **同步与创建是否同链路？** 抽 `syncDraftToAttractionLibrary`，创建与 regenerate 共用；避免 regenerate 漏调 sync 或传入被模板常量污染的 `routeDetail`。  
4. **无坐标就跳过是否合理？** 原逻辑在匹配前就要求坐标，导致「库里有、但补坐标失败」的景点也不关联；改为**先匹配、再决定是否新建 pending**（无坐标可 pending）。

### 实现原理

`regenerateRouteFromPrompt`：`generateRoute` → `normalizeRouteDetailDays` + 深拷贝 → `sync` → 更新 `travel_routes` 与 `route_detail`（含 `sourcePrompt`、`llmProviderChoice`）。`attraction-sync` 调整顺序：高德补坐标 → `resolveAttractionMatch` → 合并或 `insertPendingAttraction`。

### 最终方案

- API：`POST /api/routes/:id/regenerate`，body 同 `/generate`（`prompt`、可选 `provider`）。  
- 详情页草稿展示「修改需求重新生成」；`route_detail.sourcePrompt` 记录原始需求。  
- 重新生成后 `isUnlocked` 重置为 `false`（内容已变）。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **草稿原地迭代** | 同一路线 ID 反复调 prompt，适合 MVP 快速试错。 |
| 2 | **同步链路复用** | 创建/regenerate 共用 `syncDraftToAttractionLibrary`，景点库行为一致。 |
| 3 | **需求可追溯** | `sourcePrompt` 写入 `route_detail`，详情页可预填上次描述。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **重新生成不入库** | 根因是同步前无坐标即 return；改为先匹配、未匹配再 pending；regenerate 剥离旧 `attractionId`。 |
| 2 | **模板对象被污染** | `ROUTE_TEMPLATES` 为模块级常量；LLM/模板返回前深拷贝 `days`，避免多次生成共享引用。 |
| 3 | **已发布不可覆盖** | `status !== DRAFT` 抛错，防止已分享路线被静默替换；需改需求则复制 prompt 到规划页新建。 |

## A3-2 移动端 AI 规划全局 Loading 与中断

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-20 |
| **路线图** | A3 / C 阶段 AI 体验前置 |
| **关联代码** | `utils/ai-plan-loading.ts`、`utils/request.ts`（`requestAiPlan`）；`components/ai-plan-blocking-overlay`；`DouxingTabBar.vue`；`pages/plan/plan.vue`、`pages/routes/detail.vue` |

### 背景与目标

LLM 生成路线耗时可达数十秒，期间用户若切换 Tab 或点其他按钮会离开流程、产生重复请求。需要**全屏阻塞 + 可取消**，与后端 abort 对齐。

### 思考过程

1. **用 `uni.showLoading` 够不够？** 原生 loading 无自定义「取消」、难拦截 Tab；自定义全屏遮罩可统一文案与按钮。  
2. **遮罩放哪？** 小程序 `App.vue` 模板不盖页面；挂在**各 Tab 页的 `DouxingTabBar`** + 非 Tab 的 `detail.vue`，保证 z-index 高于 TabBar（100000）。  
3. **如何真正中断？** `uni.request` 返回 `RequestTask`，`abort()` 可取消；封装 `requestAiPlan` 注册 task，取消时 reject 为 `已取消路线规划`，业务侧不 toast 失败。  
4. **如何防跳转？** `uni.addInterceptor` 拦截 `switchTab`/`navigateTo`/`navigateBack` 等；TabBar `onSwitch` 再判 `isAiPlanLoading()` 双保险。

### 实现原理

`beginAiPlanLoading` 置 `active` 并安装导航拦截；`requestAiPlan` 在 `finally` 中 `endAiPlanLoading`；用户点「取消规划」→ `cancelAiPlanLoading` → `task.abort()`。仅 `generateRoute` / `regenerateRoute` 走该封装，其它 API 不受影响。

### 最终方案

- 全屏遮罩：转圈 + 文案 +「取消规划」。  
- 生成/重新生成期间禁用 Tab、模型选择、重复提交。  
- 取消后停留当前页，不跳转详情。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **可中断的长请求** | 用户不必杀进程或关小程序，体验接近原生「取消」。 |
| 2 | **导航双保险** | 拦截器 + TabBar 判断，降低误触切页概率。 |
| 3 | **AI 请求隔离** | `requestAiPlan` 与普通 `request` 分离，避免全站请求都带遮罩。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **全局 UI 在 UniApp 的挂载点** | 不能依赖 App 根模板；随 TabBar/详情页组件挂载遮罩，覆盖当前栈顶页。 |
| 2 | **abort 错误文案不一** | 各端 `errMsg` 含 `abort`/`cancel` 不一；`isRequestAbortedError` 统一识别，映射为固定中文提示。 |
| 3 | **取消与 complete 竞态** | `abort` 后仍会走 `fail`/`complete`；`finally` 里 `endAiPlanLoading` 幂等，避免遮罩残留。 |

## A3 路线能力补全

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-21 |
| **路线图** | A3 |
| **关联代码** | 迁移 `0007_route_engagement.sql`；`route-interaction.service.ts`、`route.service.ts`；`routes.ts`；移动端 `routes/list.vue`、`routes/detail.vue` |

### 思考过程

1. **计数存列还是实时聚合？** 热门榜需按浏览/点赞排序，若每次 `COUNT(*)` 关联表会在列表接口放大查询成本。折中：`travel_routes` 冗余 `view_count` / `like_count` / `collect_count`，用户关系表 `route_likes`、`route_favorites` 保证唯一，切换时同步增减计数。  
2. **点赞与收藏是否合并一张表？** 语义与后续通知不同，拆表更清晰；接口分别为 `POST .../like` 与 `.../favorite`，移动端独立按钮。

### 实现原理

详情 `GET` 时 `view_count + 1`；点赞/收藏 toggle 先查关系表再更新计数；列表按 scope 分支查询，对当前用户批量补齐 `isLiked` / `isFavorited`；热门排序默认 `like_count * 2 + view_count`。

### 最终方案

- 迁移新增统计列与两张关系表；`toRouteInfo` 抽到 `route-info.util.ts` 避免循环依赖。  
- API：`GET /routes`（筛选/排序）、`GET /routes/hot`、`PUT /routes/:id`、`POST .../like`、`POST .../favorite`。  
- 移动端路线 Tab：我的/热门/收藏 + 草稿状态筛选；详情页展示统计、互动；**地图路线预览动画**；草稿编辑为 hero 按钮 + 弹窗（见 A3+++）。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **列表 scope 统一入口** | 一套 `GET /routes` 查询参数覆盖我的/热门/收藏，减少客户端分支接口。 |
| 2 | **关系表 + 冗余计数** | 保证用户级唯一点赞/收藏，同时支持热门排序无需重聚合。 |
| 3 | **详情自动计浏览** | 打开详情即 +1，管理端与移动端统计口径一致。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|

## A4 订单状态机

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-21 |
| **路线图** | A4 |
| **关联代码** | `packages/shared/src/order-state.ts`；`order-transition.service.ts`、`order.service.ts`、`jobs/order-timeout.job.ts`；`routes/orders.ts` |

### 背景与目标

MVP 仅有模拟支付，缺少明确的状态流转与待支付超时关闭，易出现重复支付、僵尸待支付单。A4 要求 `pending→paid→completed/cancelled` 与超时取消。

### 思考过程

1. **状态表放 shared 还是仅 server？** 前后端都要展示状态文案，流转规则也应单一来源；`canTransitionOrderStatus` 放 `@douxing/shared`，服务端 CAS 更新放 server。  
2. **支付后是否停在 paid？** 路线解锁属数字交付，支付成功即可完结；`shouldAutoCompleteAfterPay` 对 `route` 类型在解锁后 `paid→completed`，管理端与用户列表口径一致。  
3. **防重复支付怎么做？** 仅靠读后再写会有竞态；`UPDATE ... WHERE status = expectedFrom` 乐观锁，失败返回「状态已变更」；已 paid/completed 直接拒绝。  
4. **超时用什么基础设施？** 首版无 MQ，进程内 `setInterval` 扫描 + `.env` 可配分钟数，与短信验证码 Map 策略一致，G 阶段再迁队列。

### 实现原理

`applyOrderStatusTransition` 校验合法边后按当前 status 条件更新；`payOrder` 走 `pending→paid`，解锁路线后可选 `paid→completed`；`cancelOrder` 与定时任务均走 `pending→cancelled`；创建订单时复用同用户同路线的待支付单，避免重复下单。

### 最终方案

- 共享：`order-state.ts`（流转表、文案、是否自动完结）。  
- API：`POST /orders/:id/cancel`；支付/取消均经状态机。  
- 后台：`startOrderTimeoutJob` 随服务启动，默认 30 分钟超时、60 秒扫描。  
- 环境变量：`ORDER_PENDING_TIMEOUT_MINUTES`、`ORDER_TIMEOUT_SCAN_INTERVAL_SEC`。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **流转规则单源** | shared 定义合法边，服务端与后续支付网关共用，避免魔法数字散落。 |
| 2 | **CAS 防双付** | 条件更新 + 读回校验，并发双击支付仅一笔成功。 |
| 3 | **待支付单复用** | 同路线已有 pending 则返回原单，配合超时取消减少订单膨胀。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **支付与解锁的原子性** | 先 CAS 到 paid 再解锁；解锁失败需人工/补偿（MVP 记录日志，E 阶段接真实支付回调）。 |
| 2 | **多实例定时任务** | 多 Pod 会重复扫描，靠 CAS 取消幂等；生产建议 G 阶段单消费者 或分布式锁。 |
| 3 | **已支付与已完成并存** | 数字商品支付后自动 completed；若仅展示「已支付」会误导，统一用 `getOrderStatusLabel`。 |

### 思考过程

### 最终方案

- 环境变量：`CHECKIN_GEOFENCE_ENABLED`（默认 true）。  
- 打卡响应可选带回 `distanceMeters` 便于 UI 展示「距景点 xx 米」。  
- 目标点：优先 `attractionId` 关联景点坐标，其次客户端传 `targetLatitude/Longitude`（路线节点 POI）。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **可关闭的严格模式** | 一条 env 切换演示/生产，无需改代码分支。 |
| 2 | **多层防作弊 MVP** | 精度 + 距离 + 速度，不依赖第三方风控 SDK。 |
| 3 | **错误语义化** | 距离、精度、重复打卡等分文案，方便用户自助修正。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **坐标系** | 国内地图与高德为 GCJ-02；客户端 `uni.getLocation` 与库存坐标需同一参考系。 |

## B6 排行榜

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-22 |
| **路线图** | B6 |
| **关联代码** | `services/leaderboard.service.ts`、`routes/leaderboard.ts`；`pages/leaderboard/index.vue`；`@douxing/shared` LeaderboardPeriod/Metric |

### 背景与目标

设计文档 §4.2 社交激励中的排行榜。提供周榜/月榜，按打卡次数或积分排序，并展示当前用户名次。

### 思考过程

1. **实时榜还是周期榜？** 首版做自然周/自然月聚合，SQL `GROUP BY user_id`，不做 Redis ZSET，与当前仅 MySQL 的基础设施一致。  
2. **排序指标？** `checkins` 次数与 `points` 求和二选一，接口参数 `metric`；同分再比打卡数。  
3. **是否只统计已通过打卡？** 是，过滤 `CheckInStatus.APPROVED` 与活跃用户，避免测试数据污染。  
4. **当前用户不在 Top N？** 全量聚合后在内存算 rank，返回 `myRank` / `myValue`；未上榜则 rank null、value 0。

### 实现原理

`resolvePeriodRange` 算本周一 0 点或本月 1 号；SQL aggregate → 排序 → slice limit → 补用户 nickname/avatar。周期与 metric 枚举放 shared，移动端 chip 切换触发重新请求。

### 最终方案

- API：`GET /leaderboard?period=week|month&metric=checkins|points&limit=`  
- 移动端独立排行榜页（profile 入口）。  
- 默认 limit 20，上限 shared 常量控制。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **周期边界清晰** | 周一为周起点，与中文产品习惯一致。 |
| 2 | **我的排名始终可见** | 不在 Top N 也返回 myRank，减少挫败感。 |
| 3 | **双指标一套聚合** | 同一次 SQL 结果按 metric 选排序字段，避免 duplicate 查询。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **全量聚合再 slice** | 用户量大时需 SQL LIMIT 或物化视图；MVP 用户少可接受。 |
| 2 | **服务器时区** | period 起止用 JS Date 构造，需与 MySQL 存储时区对齐。 |
| 3 | **积分与次数口径** | 积分来自 B1 计分规则变更会影响历史榜；文档说明「规则变更不追溯重算」。 |

### 思考过程

1. **生成后详情页信息过载** 用户刚生成完更关心行程节点，「编辑草稿」名称/简介块抢注意力。  
2. **编辑能力要不要删？** 不删；改名称/简介仍是有效需求，应放在 intentional 入口。  
3. **如何区分场景？** 初版用列表打开草稿时带 `?edit=1`；规划页跳转不带参，详情页内嵌编辑卡片默认隐藏。

### 最终方案（初版，已被 A3+++ 替代）

- 详情页：`showDraftEdit = isDraft && isOwner && allowDraftEdit`。  
- `我的` scope 下点击草稿：`/pages/routes/detail?id=&edit=1` 才显示内嵌编辑卡片。  
- 规划页「查看路线详情」等路径不带 `edit=1`，首屏无编辑表单。

> **后续演进**：内嵌卡片改为 hero 编辑按钮 + 弹窗；移除 `edit=1` 与自动展开；见 [A3+++](#a3-草稿编辑弹窗与发布状态)。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **零后端改动** | 纯前端路由参数区分场景，风险小。 |
| 2 | **生成流更干净** | 首屏聚焦行程与发布/追问，符合 C1 对话规划主路径。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **内嵌表单仍占版面** | 带 `edit=1` 时编辑区挤在详情中部；后续改为弹窗 + 手动点击打开（A3+++）。 |

## A3+++ 草稿编辑弹窗与发布状态

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-26 |
| **路线图** | A3 体验优化（承接 A3++） |
| **关联代码** | `pages/routes/detail.vue`；`static/iconfont/svg/edit.svg`；`i18n/locales` 中 `routes.edit*`、`routeMap.*` |

### 背景与目标

在 A3++「生成后默认不编辑」基础上，草稿仍须支持改名称/简介；同时要与**发布状态**一致（仅草稿可改，已发布/已归档不可编辑），且查看详情时不应自动弹出编辑层。

### 思考过程

1. **内嵌卡片还是弹窗？** 弹窗不占详情页纵向空间，与地图、行程列表并列更清晰；遮罩 + 取消/保存符合移动端习惯。  
2. **编辑入口放哪？** hero 卡片右上角铅笔按钮，与标题/统计同屏，草稿所有者一眼可见。  
3. **发布状态如何表达？** hero 标题旁展示状态徽章（草稿/已发布/已归档）；编辑按钮仅 `isOwner && status=DRAFT`，与后端 `updateDraftRoute` 仅草稿可 PUT 一致。  
4. **还要不要 `edit=1` 自动打开？** 否；进入详情只浏览，**必须点击编辑按钮**才开弹窗，避免误触与信息过载。  
5. **名称/简介怎么展示全？** 微信小程序单行 `input` 易截断长标题；名称与简介均用 `textarea` + `auto-height` + 按字数估算 `minHeight`。

### 实现原理

`canEditRouteInfo = isOwner && DRAFT` 控制 hero 编辑按钮；`editModalVisible` 由 `openEditModal` / `closeEditModal` 管理。弹窗内带 label（路线名称/路线简介）、滚动区 `scroll-view`、保存走既有 `PUT /routes/:id`。保存成功关闭弹窗并刷新 hero 标题与描述。

### 最终方案

- hero：标题 + 状态徽章 + 条件显示编辑按钮（SVG 图标）。  
- 弹窗：标题、说明文案（仅草稿可改）、带 label 的表单、取消/保存草稿。  
- 移除：`edit=1` query、`autoOpenEditModal`、页面内嵌 `edit-card`。  
- 列表 `goDetail` 不再拼接 `edit=1`。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **发布状态与后端一致** | 仅草稿显示编辑；已发布路线无编辑入口，避免调用 `仅草稿状态的路线可编辑` 错误。 |
| 2 | **查看与编辑分离** | 进详情默认只看内容；编辑为显式操作，符合 AI 生成后主路径。 |
| 3 | **长文案可编辑** | 名称/简介 textarea 自适应高度，弹窗 body 可滚动。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **单行 input 截断长路线名** | 改为 textarea + `auto-height` 与动态 `minHeight`。 |
| 2 | **编辑图标识别度** | CSS 伪元素铅笔在小程序上易变形；改用 `/static/iconfont/svg/edit.svg` 白色描边图标。 |
| 3 | **与 A3++ 行为迁移** | 删除 `edit=1` 后需同步更新列表跳转与文档，避免仍期望自动展开编辑。 |

## A3-3 路线详情地图预览动画

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-26 |
| **路线图** | A3 增强 / B3 地图能力延伸 |
| **关联代码** | `packages/shared/src/route-path.ts`；`packages/mobile/src/components/route-map/RouteMapPlayer.vue`；`utils/route-path-animation.ts`、`utils/route-map.ts`；`pages/routes/detail.vue` |

### 背景与目标

AI 生成路线后，用户需要在详情页直观看到 POI 空间关系与「走线」感；同时为后期「多条路线/打卡合并为一条足迹动画」预留统一路径模型。

### 思考过程

1. **动画能力从哪来？** uni-app `<map>` 的 `polyline` 无原生 draw 动画，需自研：逐帧增加折线点数 +  traveler marker 沿路径插值移动。  
2. **路径点从哪来？** `routeDetail.days` 中带坐标的 POI 按日程顺序连线；MVP 用直线插值 densify，不依赖新 API。  
3. **真实路网何时做？** 阶段 2 服务端接高德 direction + Redis 缓存；当前 shared 已留 `RoutePathSegment.mode` 与 `mergeRoutePaths`。  
4. **何时展示地图？** 与行程可见性一致：`isUnlocked` 且至少 2 个 POI 有坐标；无坐标站点计数提示 i18n。  
5. **跨端动画定时器？** H5 可用 `requestAnimationFrame`；**微信小程序无全局 rAF**，须降级 `setTimeout(16ms)`。

### 实现原理

```text
routeDetail → buildRoutePathFromDetail（shared）
    → pois / segments / fullPoints
    → RouteMapPlayer
        → createRoutePathAnimation（polyline slice + marker 插值）
        → buildRoutePoiMarkers / buildRoutePolyline
```

播放器支持播放/暂停/重播，默认自动播放约 8s。

### 最终方案

- **shared**：`extractRouteDetailDays`、`interpolateSegment`、`buildRoutePathFromDetail`、`mergeRoutePaths`（后期多路线合并）。  
- **mobile**：`RouteMapPlayer` 组件挂于路线详情解锁区；`buildRoutePoiMarkers` 为每个打卡点绘制 **常驻气泡**（`序号. 景点名`，`callout.display: 'ALWAYS'`），图钉序号圆标保留；文案键 `routeMap.*`。  
- **待办（A3-3+）**：足迹页 `mergeRoutePaths` 多路线合并动画（路网 polyline 已由 [H9-2](#h9-2-路网-polyline-与酒店-ragphase-2) 经 `GET /routes/:id/map-path` 提供）。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **路径模型在 shared** | 详情预览与后期「人生足迹」合并共用 `RoutePath`，避免重复解析 `routeDetail`。 |
| 2 | **可复用播放器** | `RouteMapPlayer` 可接入规划候选预览、足迹页，仅换数据源。 |
| 3 | **跨端动画调度** | `scheduleFrame` 自动 rAF / setTimeout 降级，H5 与微信小程序行为一致。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **微信小程序无 `requestAnimationFrame`** | 捕获 `TypeError: requestAnimationFrame is not a function`；统一用 `scheduleFrame` + `setTimeout(16)` 降级。 |
| 2 | **部分 POI 无坐标** | RAG/高德补全前过滤无坐标节点；UI 提示 `hiddenSpots` 数量，避免用户以为路线不完整是 bug。 |
| 3 | **MVP 直线穿楼** | Phase 1 接受演示级效果；[H9-2](#h9-2-路网-polyline-与酒店-ragphase-2) 已改走服务端 direction + Redis 缓存，客户端 API 失败时仍回退本地直线。 |

## G8 生产部署与 API 公有化

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-23（2026-05-24 补充 MySQL/PM2 踩坑） |
| **路线图** | G8 |
| **关联代码** | `scripts/deploy-server.mjs`、`scripts/fix-mysql-password.mjs`、`scripts/setup-debian12.sh`、`scripts/install-nginx-auto.sh`、`scripts/install-nginx-certbot.sh`、`scripts/install-nginx-ssl.sh`；`deploy/docker-compose.prod.yml`、`deploy/ecosystem.config.cjs`、`deploy/nginx/*.template`；`packages/server/src/config/env.ts`、`packages/server/src/routes/health.ts`；`docs/deploy-production.md`、`docs/启动与部署流程.md`、`docs/env-environments.md`；`packages/server/src/utils/public-asset-url.util.ts` |

### 背景与目标

微信小程序上线要求 API **HTTPS + 合法域名**。本地 `127.0.0.1:3000` 无法真机 uploadFile；需将 Node API 部署到腾讯云轻量服务器（`api.yxtao.site`），并沉淀**可重复的一键发版流程**，避免每次部署手工配 Nginx/Certbot。

### 思考过程

1. **系统选 Debian 还是 OpenCloudOS？** 轻量机常见 OpenCloudOS 的 Nginx 目录、dnf、SELinux 与文档差异大；重装 **Debian 12** 后 `apt` + `sites-available` 与社区教程一致，踩坑更少。  
2. **进程怎么守护？** 开发用 `pnpm dev:server`，生产用 **PM2** + `deploy/ecosystem.config.cjs`；MySQL/Redis 用 **Docker** 且端口只绑 `127.0.0.1`，对外仅 Nginx 80/443。  
3. **2G 内存能否跑 `tsc`？** 生产 `pnpm build:server` 在轻量机上常卡在 `@douxing/server` 的 `tsc`；改为 **tsx 直跑源码**（仍 build `@douxing/shared`），PM2 通过 `SERVER_RUNTIME=tsx` 或内存 ≤4G 自动启用。  
4. **Nginx 与 deploy 要不要分两步？** 用户每次 deploy 后再跑 certbot 体验差；从 `.env` 的 `API_PUBLIC_BASE_URL` 解析域名，`deploy:server` 末尾调用 `install-nginx-auto.sh`：**HTTPS 已通则跳过**，已有 Certbot 配置则不覆盖。  
5. **静态资源 URL 怎么给小程序？** DB 存相对路径 `/uploads/...`，接口返回时按 `API_PUBLIC_BASE_URL` 动态拼 HTTPS，避免历史 localhost 写入库。  
6. **三套环境怎么区分？** 根目录 `.env.development` / `.env.staging` / `.env.production` 管前端打包；服务器 `.env` 管后端；文档 [env-environments.md](./env-environments.md) + [启动与部署流程.md](./启动与部署流程.md) 统一说明。  
7. **改 `.env` 数据库密码后 API 仍 Access denied？** 分两类：**MySQL 数据卷**里用户密码仍是旧值（`MYSQL_*` 环境变量只在容器**首次初始化**时生效）；**PM2 进程**可能缓存旧 `DATABASE_URL`，且 `dotenv` 默认不覆盖已有环境变量——部署 shell 里 `wait-only` 能连上，PM2 内查库仍失败。  
8. **`/api/health` 能通是否代表数据库正常？** 否。health 不查库，仅返回静态 JSON；后台任务（如 `[order-timeout]`）或登录接口才会暴露真实连接问题。  
9. **改密后如何可靠发版？** 提供 `pnpm fix:mysql-password`（宿主机 `DATABASE_URL` 验证 + 容器内 `ALTER USER`）；PM2 改为 **delete + start**（不用 reload）；`env.ts` 设 `dotenv override: true`；`ecosystem.config.cjs` 启动时注入完整 `.env`。

### 实现原理

`pnpm deploy:server`：校验生产 `.env` → Docker compose 起 MySQL+Redis → `pnpm install` →（低内存则 shared build + tsx）→ 宿主机 `wait-only` 验连 → `db:migrate` → **PM2 delete + start**（注入 `.env`）→ 健康检查 → **Nginx 自动配置**。Nginx 脚本检测 `curl https://域名/api/health`，失败则写反代配置；Let's Encrypt 证书存在则装 SSL 模板，否则 HTTP + 可选 `NGINX_CERTBOT_EMAIL` 自动 certbot。

**数据库密码与连接链路**：

```text
.env（MYSQL_PASSWORD + DATABASE_URL 三处须一致）
    ↓
PM2 进程环境变量（reload 可能残留旧 DATABASE_URL）
    ↓
dotenv 加载（override: true 后以 .env 为准）
    ↓
Node API → 127.0.0.1:3307 → Docker MySQL（MySQL 侧见来源 IP 172.18.0.1）
```

改 `.env` 只影响**新启动**的 Docker 卷初始化；已有 `mysql_data` 卷须在容器内 `ALTER USER`，或 `pnpm fix:mysql-password --recreate` 清卷重建。

### 最终方案

- **一键部署**：`pnpm deploy:server --skip-docker --use-tsx`（2G 机推荐）。  
- **Nginx 合并进 deploy**：`.env` 设 `NGINX_AUTO_SETUP=true`、`API_PUBLIC_BASE_URL`；跳过：`--skip-nginx`。  
- **HTTPS**：`install-nginx-certbot.sh` 或 deploy 自动 certbot；已有证书用 `install-nginx-ssl.sh`。  
- **发版**：后端 `git pull` + deploy；小程序本地 `pnpm build:mp-weixin` 上传微信；服务器重启**不必**重配 Nginx（PM2/Docker/Nginx 开机自启）。  
- **运维文档**：`deploy-production.md`（Debian 12）、`启动与部署流程.md`（含发版 checklist）。  
- **改数据库密码**：`.env` 中 `MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD`、`DATABASE_URL` 三处一致 → `pnpm fix:mysql-password` → `pnpm exec pm2 delete douxing-api` → `pnpm deploy:server --skip-docker --skip-build`；可接受丢库时用 `pnpm fix:mysql-password --recreate`。  
- **发版后验证**：除 `curl .../api/health` 外，应用登录等查库接口或查看 `pm2 logs` 无 `Access denied`。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **deploy + Nginx 一步到位** | `API_PUBLIC_BASE_URL` 驱动域名；HTTPS 已通则自动跳过，避免重复配置。 |
| 2 | **tsx 低内存模式** | 内存 ≤4G 自动启用，跳过 server `tsc`，2G 轻量机可稳定发版。 |
| 3 | **文档化发版流程** | 开发/测试/生产启动命令、发版类型决策、重启 vs 发版区分，新人可按文档操作。 |
| 4 | **MySQL 改密工具链** | `fix:mysql-password` 以宿主机 `DATABASE_URL` 验连；`ecosystem` + `dotenv override` 保证 PM2 与 `.env` 一致。 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **Nginx 首次 SSL 与 certbot 死锁** | 模板不能预写 `listen 443 ssl` 且无证书；首次仅 HTTP:80，certbot 成功后再追加 HTTPS。Debian 12 用 `listen 443 ssl http2`，勿用 `http2 on;`。 |
| 2 | **根域证书不能给 api 子域用** | `yxtao.site` 证书 SAN 不含 `api.yxtao.site`；须单独申请子域证书或 `*.yxtao.site` 通配符，或 Certbot 签 `api.yxtao.site`。 |
| 3 | **`@douxing/shared` 未 build 导致 PM2 报错** | `package.json` exports 指向 `dist/`；`deploy:server` 必须先 build shared；tsx 模式同样依赖 shared dist。 |
| 4 | **MySQL 改 `.env` 不生效** | `MYSQL_*` 仅容器**首次**建卷时写入；已有 `mysql_data` 须 `ALTER USER` 或 `fix:mysql-password --recreate`。`DATABASE_URL` 密码须与 `MYSQL_PASSWORD` 一致。 |
| 5 | **PM2 reload 残留旧 `DATABASE_URL`** | `dotenv` 默认不覆盖进程已有变量；deploy shell 的 `wait-only` 通过但 PM2 内 `[order-timeout]` 仍 Access denied。**解决**：`pm2 delete` + 重新 start；`env.ts` 加 `override: true`；`ecosystem.config.cjs` 注入 `.env`。 |
| 6 | **health 正常但业务接口失败** | `/api/health` 不查库，不能作为数据库验收依据；应测登录等写库接口或看 `pm2 logs`。 |
| 7 | **小程序真机仍连 127.0.0.1** | 须打生产包 `pnpm build:mp-weixin`（读 `.env.production`），并在微信后台配置 uploadFile/request 合法域名；与 MySQL Access denied **无关**。 |

## G9 国际化（i18n）

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-27（框架 05-26 + 扫尾 + en-US 主流程手测验收） |
| **路线图** | G9 |
| **关联代码** | `packages/shared/src/i18n/`；`packages/mobile/src/i18n/`（含 `mobileT.ts`）、`packages/web/src/i18n/`；`packages/server/src/middleware/locale.ts`、`utils/response.ts`、`i18n/api-*`；`docs/国际化.md` |

### 背景与目标

小程序提审与潜在出海用户需要 **界面中英文切换**；API 错误与成功提示也应随语言变化，而不是硬编码中文。目标是在不破坏现有接口的前提下，建立 **shared 单源文案 + 各端 vue-i18n + 服务端 `messageKey`** 三层体系，并保留旧中文 message 的兼容映射。

### 思考过程

1. **文案放哪一层？** Tab、导航、会员等级等跨 Web/移动复用，放 `@douxing/shared`；各端页面专属文案放 `mobile` / `web` 的 `locales/*.ts`，在 `i18n/index.ts` 浅合并。  
2. **API 怎么改不炸客户端？** 响应体增加可选 `messageKey`，`message` 仍按 `Accept-Language` 翻译后返回；历史 `fail(res, '未登录')` 经 `API_LEGACY_MESSAGE_MAP` 自动映射到 key，业务可渐进迁移。  
3. **UniApp 与 vue-i18n 插值** | 部分端上模板 `t('key', { name })` 不替换占位符；移动端增加 `useTf()` + shared 的 `formatMessage` 做运行时 `{key}` 替换。  
4. **LLM 与 DB 仍是中文怎么办？** 用户兴趣标签、意图主题在库内仍存中文预设值；展示层用 `formatInterestTagLabel` / slug 映射，服务端助手回复用 `plan-messages.ts` 按 locale 生成，不把翻译塞进 prompt。  
5. **语言如何与 API 对齐？** 移动端 `request.ts` 附带 `Accept-Language`（读 `douxing_locale` 存储）；服务端 `localeMiddleware` 写入 `res.locals.locale`，`success` / `fail` 统一走 `resolveApiMessageInput`。  
6. **非 Vue 模块怎么翻译？** 定位、语音、上传 API 等纯 TS 无法 `useI18n()`；增加 `mobileT(key, params)`，内部读 `i18n.global` + `formatMessage`，与 `useTf` 插值规则一致。  
7. **状态标签怎么跨端？** 订单/路线状态不再硬编码中文 label；shared 新增 `getOrderStatusI18nKey()`，各端 `t(key)` 展示。

### 实现原理

```text
用户切换语言 → localStorage / uni.storage（LOCALE_STORAGE_KEY）
    ↓
vue-i18n locale + 各端 messages（shared ∪ mobile/web）
    ↓
HTTP 请求头 Accept-Language
    ↓
localeMiddleware → res.locals.locale
    ↓
success/fail → resolveApiMessage → { message, messageKey }
```

服务端动态文案（规划助手回复、变体标签、模板路线名）集中在 shared 的 `plan-messages.ts`、`plan-variants.ts`、`plan-route-names.ts`，由 `plan-session.service` 等传入 `locale` 参数生成。

非 Vue 模块（`location.ts`、`speech-to-text.*`、`api/speech.ts` 等）走 `mobileT()`，与界面语言同源。

## H9 住宿与交通编排（LLM 排 POI + 后端 Enricher）

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-29（**H9-1～H9-4 已全部落地**） |
| **路线图** | H9 |
| **关联代码（规划）** | `server/services/route-enricher.service.ts`；`server/services/amap-direction.service.ts`；扩展 `travel-intent.service.ts`（C2）；`shared/types.ts`；`route-generator.service.ts`；`llm-client.service.ts` / `ai-service`；`mobile/components/route-day-flow/`、`pages/routes/detail.vue` |

### 背景与目标

H9 要求生成路线含**住与行**、天数切换可见**交通耗时**、意图能识别「住哪」「怎么去」。当前 C 阶段是**单次 LLM 输出完整 JSON**（含 `poiType=hotel/transport`），交通时刻与酒店店名常由模型编造，与 A2 内容库、高德坐标链路不一致，详情页也未分区展示。

设计文档 §3.3 描述多 Agent 协作；MVP 已落地的是 **C1 多轮 + C2 意图 + C3 RAG + 管道式 generateRoute**，并非独立 Agent 协调器。H9 需在不大改架构的前提下提升「可执行感」。

### 思考过程

1. **是否新建「路径规划 Agent」？** 否。无 12306/航班/订房 API 时，独立 Agent 仍是 LLM 编造；还会增加延迟、多步 JSON 合并与调试成本。与 C5 结论一致：**编排式管道**优于过早引入 LangChain 多 Agent。
2. **LLM 一次写全 vs 分工？** 选定 **LLM 只排 POI（玩什么）**，**后端 Enricher 补交通与住宿（怎么动、住哪）**。市内耗时、顺序、时刻表用路网数据 + 确定性算法；酒店用 A2 RAG/高德 POI + 选址规则；大交通 Phase 1 用城市对模板，Phase 3 再接班次 API。
3. **和设计文档 §3.7 遗传算法的关系？** 文档 GA（种群 200）面向「候选景点很多」的组合爆炸；H9 每日 2～6 POI，采用 **Nearest Neighbor + 2-opt + 前向时间调度** 即可，可解释、易单测；GA 留作远期「从 RAG 20+ 候选里选进一天」的增强项。
4. **Enricher 挂在哪？** 放在 `generateRoute` 的 LLM/模板产出之后、`enforceRouteConstraints` 与 `applyRagToRouteDraft` 之前（或紧接其后），使 C1 追问、C4 多方案、Python/Node 降级链**共用同一补全逻辑**；用户改 POI 后交通自动重算，避免整段 JSON 漂移。
5. **与现有地图动画的关系？** `buildRoutePathFromDetail` 当前为 POI 间直线插值；Enricher 产出 `transit[]` 后，地图可只画 `attraction`+有坐标 `hotel`，路段 polyline 来自高德 direction（Phase 2），与 A3-3 动画链路衔接。

### 实现原理

```text
用户 prompt / 多轮 history
  → C2 意图（扩展 transportPreference、lodgingArea/lodgingTier）
  → C3 RAG 景点候选
  → LLM：仅输出 days[].attractions[]（name、poiType、description；time 可空）
  → route-enricher.service（确定性 + 高德 API）
       1. geocode 补坐标（复用 amap-geocode）
       2. assignLodgingPerDay：hotel RAG/POI + 设施选址（最小化到当日 POI 路网耗时和）
       3. buildDailySchedule：Distance Matrix → 最近邻排序 → 2-opt → 选 walk/transit/drive → 前向排时刻
       4. injectIntercitySegments：跨城日 intercity 段（Phase 1 模板；Phase 3 班次 API）
       5. validateTimeWindows + budgetRollup
  → enforceRouteConstraints + applyRagToRouteDraft（现有）
  → 写入 travel_routes / plan_session snapshot
```

**算法与数据分工（摘要）**

| 子问题 | 方法 | 数据依赖 |
|--------|------|----------|
| 市内 POI 顺序 | 最近邻 + 2-opt | 高德 Distance Matrix / Direction |
| 路段耗时与方式 | 规则阈值（如 &lt;800m 步行）+ API 分钟数 | 高德 |
| **玩法动线与段间交通** | **Phase 4 玩法 RAG** + 多候选比选 | **`route_playbooks` / 模板路线 / 攻略摘要** |
| 每日时刻表 | 前向调度 + 开放时长窗检查 | POI 默认游玩时长；attractions `openHours` |
| 酒店 | RAG/DB 候选 + 加权选址 | A2 `category=hotel`；高德 POI 兜底 |
| 大交通 | 约束匹配 + 耗时估算 | Phase 1：`city-pair` 模板；Phase 3：12306/航班 |
| 综合评分 | 轻量加权（体验/预算/时间/多样性） | 可选用于 C4 多方案选优 |

**Schema 扩展（`@douxing/shared`）**

- `RouteTransitSegment`：`kind`（intercity/local）、`mode`（train/flight/subway/taxi/…）、`from/to`、`time`、`durationMinutes`、`cost`、`bookingUrl?`（mock）。
- `RouteDayPlan`：增加 `lodging?`、`transit?[]`；`attractions` 保持兼容，专指游玩 POI。
- `TravelIntentSnapshot`：增加 `transportPreference`、`lodgingArea`、`lodgingTier` 等。

**LLM Prompt 变更**：system prompt 要求**不要**编造交通段与酒店时刻；笼统用餐仍 `poiType=meal`（A2++ 规则不变）。Node 与 Python `ai-service` prompt/schema **同步收窄**。

### 最终方案（分 Phase）

| Phase | 交付 | 验收 |
|-------|------|------|
| **1 — MVP** | shared 类型 + C2 交通/住宿意图 + Enricher 骨架 + 市内 matrix 排程 + 跨城 mock 模板 + **详情页行程流程图** + i18n | 生成路线含结构化 transit/lodging；详情解锁后可见完整路径；意图识别「高铁/住西湖边」 |

| **3** | 12306/航班 API；开放时间表；Enricher 闭馆 `warnings` | 大交通可订票向；与设计文档 §3.7 对齐 |
| **4 — 玩法 RAG** | 玩法知识库 + Playbook RAG；段间 mode 比选；LLM 动线骨架；规则止血（景区不猜地铁） | 西湖等景区推荐步行/观光车；段间方式与攻略一致；流程图可选展示推荐理由 |

## H9-1 UI 行程流程图与展示策略

| 项 | 说明 |
|----|------|
| **完成日** | 2026-05-27 |
| **路线图** | H9-1g |
| **关联代码** | `mobile/src/utils/route-day-flow.ts`；`mobile/src/components/route-day-flow/RouteDayFlowChart.vue`；`mobile/pages/routes/detail.vue`；`mobile/pages/plan/plan.vue`（已移除对话区预览） |

### 背景与目标

H9-1 后端已产出 `transit[]` 与 `lodging`，详情页需让用户一眼看懂**整日动线**（先怎么去、再玩什么、晚上住哪），而不是三个独立列表。规划页 C1 对话区信息密度已高，不宜再塞完整行程图。

### 思考过程

1. **三分区列表还是一条时间轴？** 交通/游玩/住宿按时刻交错，分区列表会打断阅读顺序；竖向流程图 + 颜色区分类型（蓝/绿/紫）更贴近「路径」心智。
2. **规划页要不要预览？** 首版在对话末尾加过预览，产品反馈对话区应聚焦消息与候选切换；**完整路径只在路线详情页展示**，规划页通过「查看详情」跳转。
3. **节点怎么排序？** `buildRouteDayFlow` 解析 `time` 字段为分钟序；无时刻时回退为 transit → play → lodging 默认顺序。
4. **多日怎么切？** 顶部横向 Tab；单日隐藏 Tab 只显示 day 标题。

### 实现原理

```text
RouteDayPlan（transit + attractions + lodging）
    → buildRouteDayFlow() → RouteFlowNode[]
    → RouteDayFlowChart（竖向 rail + 卡片）
    → detail.vue（解锁后 + 打卡 emit）
```

交通节点 meta 展示「方式 · 时长」；跨城段与 `estimated` 段有 badge；warnings 仍在流程图下方按日展示。

### 最终方案

- 组件 `RouteDayFlowChart`：可复用 props（`showTitle`、`showCheckIn`、`initialDayIndex`）。
- **详情页**：解锁后展示流程图 + 打卡按钮。
- **规划页**：不展示流程图；候选卡片 + 进详情查看完整路径。
- i18n：`routes.flowChartTitle`、`flowChartEmpty`、`flowDayTab`、`flowIntercity` 等。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **一条路径读懂整日** | 交通→游玩→住宿按时间序合并，比三分区更符合出行叙事 |
| 2 | **对话与详情职责分离** | 规划页专注对话与选方案；详情页专注可执行行程 |
| 3 | **组件可复用** | 同一 chart 可用于后续 Web 管理端预览或候选方案对比（未做） |

### 重难点

### 背景与目标

### 思考过程

1. **polyline 算在客户端还是服务端？** 高德 Key 不宜下发小程序；direction 配额需 Redis 缓存；故新增 `GET /routes/:id/map-path`，在服务端基于已有 `routeDetail` 补 polyline，不重复存库。
2. **路段 mode 从哪来？** 不另猜交通方式：市内段匹配 Enricher `transit[]` 的 `from/to`；跨城段取当日 `kind=intercity` 的 mode，与 [H9-1 UI](#h9-1-ui-行程流程图与展示策略) 流程图一致。
3. **酒店 RAG 与景点 RAG 是否共用？** 独立 `retrieveHotelsForLodging`：`category=hotel` 过滤 + 区域/档次/主题加权，Enricher 再按到 POI 距离选址，写入 `attractionId` 与 `source`。
4. **客户端失败怎么办？** `detail.vue` 请求 map-path 失败时回退 `buildRoutePathFromDetail` 本地直线，保证 A3-3 播放器始终可演示。

### 实现原理

```text
routeDetail（含 enrich transit/lodging）
  → buildRoutePathFromDetail（shared，POI 序列 + 直线段骨架）
  → buildRouteMapPathFromDetail
       → 每段 findTransitModeForSegment → getDirectionPolyline（walk/drive）
       → polyline-cache（Redis 7d，坐标对排序 key）
       → 跨城 / API 失败 → 直线 + estimated: true
  → GET /routes/:id/map-path
  → detail.vue → RouteMapPlayer

Enricher 酒店：retrieveHotelsForLodging → 距离加权 → lodging（内容库优先）
```

### 最终方案

- 服务端：`route-map-path.service.ts` + `polyline-cache.service.ts`；`amap-direction.service.ts` 扩展 walking/driving direction 解析 steps polyline。
- API：`GET /api/routes/:id/map-path`（需登录 + 路线解锁权限，与详情一致）。
- 移动端：解锁后 `fetchRouteMapPath`，失败降级本地路径；`RoutePathSegment.estimated` 可在 UI 标注估算路段（与 i18n 流程图 badge 呼应）。
- Enricher：住宿候选改走 `retrieveHotelsForLodging`，无内容库命中时仍 geocode 兜底。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **地图与流程图一致** | 路段 mode 来自 Enricher `transit`，polyline 来自高德 direction，替代 POI 间直线 |
| 2 | **渐进降级** | 无 Key / API 失败 → 直线插值 + `estimated`；客户端 API 失败回退本地 `buildRoutePathFromDetail` |
| 3 | **酒店内容库优先** | RAG 打分（区域/档次/主题）+ 到 POI 距离加权；写入 `attractionId` 与 `source` |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **direction 配额与延迟** | 按路线段并行请求 + Redis 缓存（坐标对排序 key，TTL 7 天）；与 H9-1 matrix 缓存分离前缀，避免混键 |
| 2 | **transit 与 POI 名对齐** | `findTransitModeForSegment` 用 Enricher 的 `from/to` 字符串匹配；对不上则按距离阈值默认 walk/drive |
| 3 | **内容库酒店稀疏** | `cityCode` 与 `city` 双路查询；无 hotel 行时仍 geocode，但 `source` 区分 content vs amap |
| 4 | **旧路线无 enrich** | 无 `transit[]` 时 direction 仍可用默认 mode；完整体验仍须重新生成路线 |

### 背景与问题（用户反馈）

用户在 **西湖** 等景区游玩时，详情流程图出现 **「坐地铁」** 等不合理段间交通。根因并非 LLM「搜了全网」，而是：

1. **C3 景点 RAG** 只解决「玩什么 POI」，不包含「两点之间怎么走」。
2. **Enricher** 用 `getTravelDuration` + 旧版距离规则：距离 &gt;800m 且驾车耗时 ≤25 分钟 → 标记为 `subway`，**未调用任何地铁线路 API**。
3. 缺少 **景区语义**（环湖步行、观光车、游船）与 **攻略级热门动线**。

**玩法 RAG** 目标：检索「经典怎么玩 + 段间交通共识」，再交给 LLM 排 POI、Enricher 排时刻与 mode，使推荐可解释、可执行。

### 思考过程

1. **景点 RAG vs 玩法 RAG 是否合并？** 不合并表结构职责：景点库管 POI 实体；玩法库管 **动线 + 段间边**（from/to/mode/hint）。检索时可先 playbook 定骨架，再 C3 填 POI 细节。
2. **是否实时「搜全网」？** Phase 4 先做 **自建 playbook 库**（官方导览、现有 `route-templates`、人工攻略摘要），质量可控；远期再接网页检索更新 playbook，而非让 LLM 每次裸搜。
3. **Enricher 还要不要高德？** 要。Playbook 定 **mode 优先级与理由**；高德 Matrix/Direction 做 **耗时校验与 `estimated` 标注**；二者冲突时 playbook 优先、高德兜底。
4. **能否先小步交付？** **H9-4a** 独立止血（去除虚假 `subway`）；**H9-4b～d** 同日完成完整玩法 RAG 链路。

### 思考过程

1. **Token 放哪？** 延续 H1-a，集中在 `theme.css`；新增 `.theme-teal` / `page.theme-teal` **主辅色对调**（蓝主青辅 ↔ 青主蓝辅），避免各页散落 hex。  
2. **主题怎么存？** `useTheme()` + `uni.setStorageSync('douxing_app_theme')`；**`App.vue` `onLaunch` 调 `initAppTheme()`**，避免冷启动闪默认色；各页根节点 `:class="themeClass"`。  
3. **Tab 页布局怎么拆？** 参考路线 Tab：`height: 100vh` + `flex` 列；**Hero 单独 `page-header`**；快捷入口/列表进 **`page-content` scroll-view**；`DouxingTabBar` 与 scroll 同级。首页、我的页均按此改造。  
4. **何时允许滚动？** `syncPageLayout()` 用 `createSelectorQuery` 比较 `.page-body` 与 `.page-content` 高度，动态 `:scroll-y="contentNeedsScroll"`，内容够放则禁用纵向滚动。  
5. **子页（非 Tab）怎么统一？** 打卡/成就/徽章/排行榜/订单等采用 **page-hero（渐变 + emoji + 标题/副文案）+ filter-panel + page-body 卡片**，与 [品牌视觉规范 §8](./品牌视觉规范.md) 对齐。  
6. **首页热门路线怎么更「可传播」？** 在保持卡片字段不变前提下，横向 `scroll-view` 改为 **`swiper` Cover Flow**：居中放大、两侧缩小+模糊+3D 旋转；测量卡片高度设定 swiper 高度，避免固定 `min-height` 撑高页面。

### 实现原理

```text
theme.css（--dx-* + .theme-teal 覆盖）
    ↓
```

1. **Canvas 放哪一层？** 不引入服务端渲染；统一 `packages/mobile/src/poster/` 管线（payload → 模板 → Canvas → PNG），H2-b 打卡海报可复用。

5. **i18n 怎么不破版？** 海报文案走 `routes.poster.*`；英文路线名/POI 较长时模板内 `wrapText` 换行（v0.8.6 起描述与副标题不再 80 字截断）。


## D5 补全 · 海报二维码与行程全量展示

| 项 | 说明 |
|----|------|
| **完成日** | 2026-06-01（v0.8.7） |
| **路线图** | D5 补全（承接 D5-a） |
| **关联代码** | `packages/mobile/src/poster/draw-qr-code.ts`、`load-poster-image.ts`、`build-poster-payload.ts`、`poster-layout.ts`、`draw-kind-badge.ts`、`templates/diary-page.ts`；`RoutePosterSheet.vue`；`pages/share/route.vue`；`packages/server/src/routes/share.ts`、`services/wechat-mini.service.ts`、`services/share.service.ts` |

### 背景与目标

用户反馈：海报底栏 **二维码空白**（仅半透明占位）；日记卡片 **内容被裁切** 且出现「还有 N 项」却不展开。根因分别为：小程序包未配 H5、Canvas 无法直接加载 base64 小程序码、payload **人为截断**（每天 8 节点 / 5 天），以及标题行 **测高与绘制不一致**。

### 最终方案

**海报 QR（三层兜底，优先级从高到低）**

1. **H5 QR**：`VITE_H5_BASE_URL` + `qrcode-generator` → `{base}/#/pages/share/route?id=`  
2. **小程序码 PNG**：`GET /api/share/routes/:id/wxacode` → 微信 `getwxacodeunlimit`（`scene=id={routeId}`，`page=pages/share/route`）→ 小程序端 **写 USER_DATA_PATH 临时文件** 再 `canvas.createImage`  
3. **URL Link QR**：上述失败时 `GET /api/share/routes/:id/link` → `generate_urllink` → 客户端 `drawQrCode`

**行程全量展示**

- 取消 `MAX_ITEMS_PER_DAY=8`、`MAX_DISPLAY_DAYS=5`；payload 输出 **全部天数、全部 flow 节点**（交通/游玩/住宿）。  
- 不再生成「还有 N 项 / 还有 N 天」；画布高度由 `measurePosterHeight` 随内容增高（上限 **4096px**，微信小程序 Canvas 硬限制）。

**版式修复**

- `measureItemTitleRowHeight` 与 `drawItemTitleRow` 对齐，避免日记卡片白底矮于内容。  
- 生成分享码：已 **发布** 即可（`assertPublishedRouteForPoster`）；只读 H5 API 仍要求 **广场公开**。

### 配置速查

| 变量 | 文件 | 作用 |
|------|------|------|
| `VITE_H5_BASE_URL` | `.env.development` / `.env.staging` / `.env.production` | 打包时写入小程序/H5；H5 二维码 |
| `MP_WEIXIN_APPID` | 根目录 `.env`（服务端） | 小程序码 / URL Link |
| `WECHAT_MINI_APP_SECRET` | 根目录 `.env`（服务端） | 同上 |
| `WECHAT_MINI_ENV_VERSION` | 可选，`develop` / `trial` / `release` | 体验版/正式版小程序码 |

改 `VITE_*` 后须 **重新编译** 小程序；改服务端密钥后须 **重启 API**。

### 重难点

| # | 重难点 | 说明 |
|---|--------|------|
| 1 | **小程序 Canvas 不支持 data URL 图** | 小程序码须 `writeFile` 到本地路径再绘制 |
| 2 | **生产包无 VITE_H5** | 依赖服务端微信配置；`api.yxtao.site` 的 `.env` 须同步 AppSecret |
| 3 | **超长路线 >4096px** | 平台裁切；极端行程需 H2-a+ 用户自选条数或分页海报（远期） |

## H2-b 验收扫尾 · 海报主题底纹与模板体验

| 项 | 说明 |
|----|------|
| **完成日** | 2026-06-02（v0.8.9） |
| **路线图** | H2-b+（验收反馈修复） |
| **关联代码** | `poster/draw-poster-background.ts` · `poster/templates/checkin-map.ts` · `poster/templates/achievement-showcase.ts` · `poster/templates/diary-page.ts` · `poster/templates/timeline-columns.ts` · `components/poster/PosterThemeChipRow.vue` · `CheckInPosterSheet.vue` · `GamificationPosterSheet.vue` |

### 背景与目标

v0.8.8 实机验收反馈三类问题：（1）海报整体背景仅为纯色，希望主题可切换且带图案；（2）打卡足迹地图点位文字重叠，希望**照片缩略图 + 短标签**；（3）徽章海报双列卡片标题左侧被裁切。

### 思考过程

1. **主题色 vs 整页背景？** H2-a+ 的 `themePresetId` 原先只驱动分天 `themeColor`；用户期望的是**整页纸感 + 底纹**。→ 新增 `fillThemedBackground` 与 `POSTER_THEME_VISUALS`，四套主题各配横线/圆点/波浪/斜纹组合。  
2. **炫耀海报要不要单独选项 UI？** 与路线海报共用 `loadStoredPosterRenderOptions`，抽取 `PosterThemeChipRow` 组件，打卡/成就 Sheet 均可切换主题并即时重绘。  
3. **足迹点重叠怎么办？** 纯地理投影在相近城市会堆叠。→ 投影后做 **斥力 spread**（最小间距 ~92px），标签截断至 6 字；有 `photoUrl` 时绘 56px 圆角缩略图 + 序号角标。  
4. **徽章标题为何缺字？** 绘制 emoji 后 `textAlign` 仍为 `center`，`wrapText` 以左坐标为中心绘字，导致左半边出画布。→ 每卡片 `save/restore` 并强制 `textAlign: 'left'`；布局改为左图标 + 右文案。

### 最终方案

| 问题 | 方案 |
|------|------|
| 纯色背景 | `fillThemedBackground(ctx, w, h, themePresetId)` 替代各模板 `fillPaperBackground`；`resolvePosterColors` 同步 ink/accent/footer |
| 足迹重叠 | `spreadMapPoints` + 圆角 `photoUrl` 缩略图 + 短地名标签；Sheet 预加载全部打卡照片 |
| 同城多次打卡叠点 | payload **按城市聚合**（与「N 城市」一致）；投影前/后双层分散 + 环形兜底布局 |
| 徽章裁切 | `drawBadgeGrid` 横向卡片；修复 `textAlign` 状态泄漏 |

### 重难点

| # | 重难点 | 说明 |
|---|--------|------|
| 1 | **Canvas 文字对齐状态** | emoji 居中绘制后必须重置 `textAlign`，否则 `wrapText` 错位裁切 |
| 2 | **spread 与地图边界** | 斥力迭代后 clamp 到内框，避免缩略图出界 |
| 3 | **主题跨 Sheet 一致** | 炫耀海报与路线海报共享 storage key，避免用户重复配置 |

### 背景与目标

Phase 0 仅有运营上传；新生成路线 POI 无封面，手帐/行程路径观感差。Phase 1 目标：**高德 POI 图自动拉取 → 本地持久化 → 注入路线展示**，且不无限占用磁盘。

### 思考过程

1. **何时拉图？** 路线同步入库后立刻需要封面；纯 fire-and-forget 导致首屏无图。→ **sync 结束 await 批量拉图**，读详情时再兜底补拉。  
2. **pending 景点读不到？** 注入封面原用 `getAttractionsByIds`（仅 active），AI 新建多为 pending。→ **`getAttractionsByIdsForRouteMedia`（active + pending）**。  
3. **磁盘会爆吗？** 图片在**磁盘**非内存；曾用 `{id}-amap-{timestamp}` 会堆文件。→ **每景点固定 `{id}-amap.*` 覆盖** + 更新封面时删旧文件。  
4. **合规？** 不爬虫；`image_source=amap`、`image_attribution` 写高德 POI 来源；不覆盖 `manual` 上传。

### 实现原理

```text
syncAttractionsFromRouteDetail
  → 新建/合并且无封面 → 收集 ID
  → await enrichAttractionCoversForIds（高德 place/text → detail → download → DB）
  → schedule 队列仅作兜底

getRouteById / share
  → enrichRouteDetailWithAttractionCovers
  → getAttractionsByIdsForRouteMedia
  → 仍无封面则再 await 补拉（最多 16 条）
  → 注入 routeDetail.days[].attractions[].coverImageUrl
```

### 最终方案

- **高德**：`place/text extensions=all` 取 photos，无图则 `place/detail` 回退。  
- **存储**：`packages/server/uploads/attractions/{id}-amap.jpg`（单景点最多 1 张 amap 图）。  
- **CLI**：`pnpm enrich:attraction-images`（支持 `--dry-run`、`--limit=N`）。  
- **环境**：`AMAP_WEB_KEY`、`AMAP_IMAGE_ENRICH_ENABLED`、`AMAP_IMAGE_FETCH_DELAY_MS`。

## I1 ML 训练数据生成与校验

| 项 | 说明 |
|----|------|
| **完成日** | 2026-06-01 |
| **路线图** | I1 / C6 |
| **关联代码** | `packages/server/src/scripts/generate-training-dataset.ts`、`validate-training-dataset.ts`；`services/training-data.service.ts`；`services/llm-route-generator.service.ts`；`packages/ml-training/`（`prompts-seed.jsonl`、`configs/distill-qwen-7b-lora.yaml`）；根脚本 `pnpm ml:generate-dataset`、`pnpm ml:validate-dataset` |

### 背景与目标

[阿里云专属模型操作指南](./阿里云-兜行专属模型训练与部署.md) 阶段一要求：在 **不改变 RAG + Enricher 架构** 的前提下，用 DeepSeek 批量产出 SFT 训练 JSONL，且 assistant 输出须与线上 **同一套 Zod schema** 对齐（只含 POI，不含 transit/lodging）。目标是为 PAI LoRA 微调（I2）提供可校验、可划分的数据集。

### 思考过程

1. **训练样本从哪来？** 不能手抄 JSON；应复用线上 `C2 意图 → C3 RAG → H9-4 playbook → DeepSeek generateRouteFromLlm` 全链路，保证 prompt 与生产一致。  
2. **assistant 里要不要 enrich 字段？** 不要。`draftToLlmTrainingPayload` 过滤 `hotel/transport`，与 LLM prompt 收窄（H9-1f）一致；交通/住宿仍由 Enricher 在线补全，模型只学「玩什么」。  
3. **如何保证数据质量？** 生成时用 `llmRouteSchema.safeParse` + **POI 命中率**（相对 RAG 候选白名单 ≥90%）；不合格行跳过，避免脏数据进 train。  
4. **脚本放哪？** 逻辑在 `packages/server`（可访问 DB RAG 与 LLM）；产物落在 `packages/ml-training/datasets/`，与 LoRA 配置同目录，便于上传 OSS。

### 实现原理

```text
prompts-seed.jsonl
  → generate-training-dataset.ts（逐条）
       C2 buildIntentFromHistory
       → C3 retrieveAttractionsForPlanning
       → H9-4 retrievePlaybooksForPlanning
       → generateRouteFromLlm（DeepSeek）
       → buildTrainingSample（system+user+assistant JSON）
       → validateTrainingSample（Zod + POI hit rate）
  → generated/raw.jsonl
  → validate-training-dataset.ts --split
  → train.jsonl / val.jsonl（默认 9:1）
```

`buildTrainingSample` 调用 `buildRoutePlannerMessages`，assistant 内容为 `JSON.stringify(draftToLlmTrainingPayload(draft))`，与 Node LLM 训练目标一致。

### 最终方案

- 根命令：`pnpm ml:generate-dataset`（可选 `--limit`、`--delay-ms`、`--seed`）；`pnpm ml:validate-dataset -- --split`。  
- 前置：`DEEPSEEK_API_KEY` + MySQL（RAG 检索）；种子见 `packages/ml-training/datasets/prompts-seed.jsonl`（可扩充城市/主题）。  
- 校验：`validateTrainingSample` 检查 JSON 合法、days 与 routeDetail.days 一致、POI 命中率阈值。  
- 下一步（I2）：上传 train/val 至阿里云 OSS → PAI Model Gallery LoRA，见 [阿里云 doc §3～§5](./阿里云-兜行专属模型训练与部署.md)。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **复用生产 prompt 链** | 意图/RAG/playbook/LLM 与线上一致，微调后行为漂移风险低 |
| 2 | **Schema 单源校验** | `llmRouteSchema` 同时用于推理与造数，JSON 合法率可量化 |
| 3 | **POI 命中率门禁** | 默认 ≥90% 相对 RAG 白名单，减少模型学「库外幻觉 POI」 |
| 4 | **与 Enricher 解耦** | 训练目标不含 transit/lodging，职责边界与 H9 架构一致 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **DeepSeek 配额与耗时** | 种子逐条生成 + `--delay-ms` 限流；失败/校验不通过计入 skip，可重跑补量 |
| 2 | **种子覆盖不足** | 初版 `prompts-seed.jsonl` 条数有限；I2 前须按 TOP 城市/主题扩充 seed |
| 3 | **RAG 库小城市 miss** | 无 city 或库内无 POI 时命中率低会被 skip；与 C3 内容库扩充联动 |
| 4 | **train/val 划分简单** | 当前为顺序 slice 9:1；数据量大后应按 city/主题分层抽样 |

### 下一步（承接 I2）

1. 扩充 `prompts-seed.jsonl`（目标 ≥200～500 条有效样本）。  
2. 执行 `pnpm ml:validate-dataset -- --split`，上传 OSS。  
3. 按 `distill-qwen-7b-lora.yaml` 在 PAI 发起 LoRA；完成后 I3 百炼 Endpoint 接入 `llmProvider`。

## J1～J4 旅程相册（数据模型 · 配额 · UI · 打卡/手帐打通）

| 项 | 说明 |

| **文档** | [旅行照片存储系统.md](./旅行照片存储系统.md) |

### 背景与目标

旅行照片应跟 **路线行程** 归档（按天/POI），而非散落在打卡记录或本地相册；会员等级决定可存张数与容量；手帐海报需要优先用相册里的「旅程图」。

### 思考过程

1. **一路线多相册还是一相册？** 用户心智是「这次成都之旅的照片」= 一条路线；`(user_id, route_id)` 唯一约束保证一本相册，避免列表里重复路线入口。  
2. **分组存表还是 JSON？** `travel_photos` 行级存 `day_index` / `poi_name` / `attraction_id`，服务端按字段聚合 `groups`；比纯 JSON 更易 PATCH、分页与 EXIF 批处理。  
3. **配额放用户表还是单独计？** `MEMBER_PHOTO_QUOTAS`（`@douxing/shared`）按 `MemberLevel` 映射张数/字节；上传前 `assertPhotoQuota`，删除后回写 `bytes_used` / `photo_count`。  
4. **打卡图要不要双写？** 打卡仍保留 `check_in` 照片字段；创建打卡后 `ingestCheckInPhotosToAlbum` 复制进相册并标记 `source=checkin`，手帐与相册 URL 一致。  
5. **开发环境没 OSS？** 与景点封面同策略：`uploads/photos/{userId}/` + `API_PUBLIC_BASE_URL` 拼 URL；生产走 G2 OSS `photos/` 前缀。

### 实现原理

```
POST /journey-albums/:id/photos (multipart)
  → 校验 MIME/大小 → 写盘/OSS → insert travel_photos
  → 更新 album 计数与 bytes_used

POST /checkins（带图）
  → checkin.service → ingestCheckInPhotosToAlbum

RoutePosterSheet 打开
  → fetchJourneyAlbumByRoute → buildJourneyPosterMaps(groups)
  → journeyHighlightByDay[] + journeyPhotoByPoiKey 注入 poster payload
```

`buildJourneyPosterMaps`：按 `groups` 遍历，天维度收集 highlight URL；POI 键 `a:{attractionId}` 或 `d:{day}::{poiName}`，同 POI 取首张。

### 最终方案

| 层 | 交付 |
|----|------|
| 后端 | 相册 CRUD · `by-route` 幂等创建 · 全站 `/photos` 分页 · `GET /users/me/storage` |
| mobile/pc | 路线详情「相册」Tab：上传 · 按天/POI 展示 · 整理未分配区 |
| mobile | 「我的相册」：全站照片列表 + 存储用量摘要 + 选路线上传 |
| pc | 「我的相册」：相册卡片列表 + 详情页上传（J5++） |
| 打通 | 打卡归并 · 手帐 `buildJourneyPosterMaps` 优先相册图 |

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **路线即相册边界** | 与产品「一次旅行一本册」一致，查询与分享 token 都挂在 album 上 |
| 2 | **配额单源** | `MEMBER_PHOTO_QUOTAS` + `PHOTO_QUOTA_ENFORCE` 环境开关，联调可关硬顶 |

## J5 EXIF 智能归类与相册 H5 分享

| 项 | 说明 |
|----|------|
| **完成日** | 2026-06-10 |
| **路线图** | J5 |
| **关联代码** | `utils/exif.util.ts` · `travel-photo-suggest.service.ts` · `journey-album.service` `applyExifSuggestionsForAlbum` / `setAlbumShareState` · 迁移 `0024_journey_album_share.sql` · mobile/pc `ShareJourneyAlbumView` / `pages/share/journey-album` |
| **常量** | `PHOTO_EXIF_GPS_HIGH_M=500` · `PHOTO_EXIF_GPS_MEDIUM_M=2000`（`@douxing/shared`） |

### 背景与目标

用户批量上传后大量照片落在「未分配」；需用 EXIF GPS/拍摄日期建议归入路线 POI；并支持生成 **只读 H5 分享页**（类似路线分享 D5-a）。

### 思考过程

1. **上传时自动归类还是建议？** 自动写入可能错 POI（GPS 漂移、景点坐标缺失）；上传响应附带 `placementSuggestion`，默认 **不自动改库**，用户确认或批量「应用建议」。  
2. **POI 候选从哪来？** 从 `routeDetail.days[].attractions` 收集名称与坐标；缺坐标则按 `attractionId` 查 `attractions` 表补全。  
3. **距离阈值怎么定？** 500m 高置信、2000m 中置信（`haversine`）；仅日期匹配时降为 `date` 原因、置信 `low`。  
4. **分享鉴权模型？** `share_enabled` + 随机 `share_token`（32 hex）；公开 API `GET /api/share/journey-albums/:token` 无需 JWT；关闭分享仍保留 token 便于再次开启。  
5. **迁移为何曾导致「加载相册失败」？** SQL 文件存在但 `drizzle/meta/_journal.json` 未登记 `0024`，本机未跑迁移缺列 `share_enabled`；补 journal 后 `pnpm db:migrate` 恢复。

### 实现原理

```
上传 buffer → parseImageExif → takenAt / lat/lon / shootingParams
  → suggestPhotoPlacement(routeDetail, candidates, exif)
  → 响应 TravelPhotoInfo + placementSuggestion（可选）

POST apply-exif-suggestions
  → 筛未分配照片 → 有 suggestion 且 confidence≠none → PATCH day/poi

POST /journey-albums/:id/share { enabled }
  → 开启时生成 shareToken → 返回 sharePath（前端路由 /share/journey-albums/:token）
```

### 最终方案

- **EXIF**：`exif-parser` 读 buffer；GPS 与 `DateTimeOriginal` 写入 `travel_photos`。  
- **智能归类 API**：`POST .../photos/apply-exif-suggestions`，可选 `photoIds` 限定范围。  
- **分享**：mobile `pages/share/journey-album` · pc `/share/journey-albums/:token` 只读展示分组照片。  
- **i18n**：超额/无权限等走 `ApiMessageKey`。

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **建议与应用分离** | 减少误归类投诉；批量应用适合「整批原图上传」场景 |
| 2 | **与路线 enrich 同坐标系** | POI 候选来自已发布路线结构，和流程图/地图 POI 一致 |
| 3 | **分享与路线分享平行** | token 只读、无登录；与 `GET /share/routes/:id` 同一产品范式 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | **无 GPS 仅日期** | `suggestDayIndexFromTakenAt` 对齐 `days[].date`；POI 取当天第一个景点，置信低 |
| 2 | **景点无坐标** | `collectRoutePoiCandidates` 批量查 `attractions`；仍无坐标则该 POI 不进 GPS 候选 |
| 3 | **Drizzle journal 与 SQL 漂移** | 新增迁移必须同步 `_journal.json`；否则 `db:migrate` 跳过文件、运行时报缺列 |

## J5+ 我的相册上传 · 拍摄参数与同参数拼图

| 项 | 说明 |

### 背景与目标

用户不必先进路线详情也能上传；专业用户希望看到 EXIF 拍摄参数，并把 **同机身/同 ISO/光圈/快门** 的照片拼成一张图导出。

### 思考过程

1. **拍摄参数存哪？** `travel_photos.shooting_params` JSON，与 EXIF 解析同次上传写入；旧图无字段，客户端用 `hasMatchableShootingParams` 控制按钮显隐。  
2. **「同参数」如何定义？** `@douxing/shared`：`shootingParamsMatch` 对双方非空字段比较，至少 2 项一致；机型 normalize 后比对；光圈/快门/焦距带容差。  
3. **我的相册上传流程？** 选路线 →（PC）本地预览队列 → 点「上传 N 张」才 `fetchJourneyAlbumByRoute` + 逐张 `uploadJourneyAlbumPhoto`；**选图阶段不调 API**。  
4. **PC 为何多次「选图无反应」？**  
   - 早期在 `selectRoute` 回调里 `closeRoutePicker()` 清空 `pendingRouteId`，导致 `submit` 被跳过。  
   - 文件选择器关闭后遮罩 `click` 误触关闭弹窗、清空预览。  
   - `input[type=file]` 用 `display:none` 时部分浏览器 `change` 不稳定。  
5. **multipart Content-Type？** axios 手动设 `multipart/form-data` 会丢 boundary，改由浏览器自动带 boundary。

```
parseImageExif → shootingParams 写入 DB

RouteJourneyAlbumPanel 整理弹窗
  → formatShootingParamsSummary 展示
  → findPhotosWithSameShootingParams → Canvas 拼图导出

MyAlbumUploadBar（mobile）
  → partitionTravelPhotoFiles · 选路线 · 最多 9 张/次

AlbumPhotoUploadBar（pc 详情页，J5++）
  → 同上传管线 · 批量 20 · 拖拽 · 预览确认后 submit
```

## P5 Webhook 自动发版与增量 deploy

| 项 | 说明 |
|----|------|
| **完成日** | 2026-06-11 |
| **路线图** | P5 |
| **关联代码** | `scripts/gitee-webhook-server.mjs`、`scripts/gitee-webhook-deploy.sh`、`scripts/detect-deploy-targets.mjs`、`scripts/deploy-release.mjs`、`scripts/deploy-pc-site.sh`、`scripts/deploy-web-site.sh`、`scripts/install-webhook-service.sh`；`deploy/snippets/douxing-webhook.conf` |
| **关联文档** | [发版流程与CI-CD解析.md](./发版流程与CI-CD解析.md)、[服务端命令手册.md](./服务端命令手册.md)、[deploy-production.md §10](./deploy-production.md) |

### 背景与目标

P0～P4 完成后，PC/Web 静态站点与后端 API 需**可重复、低人工**地上线。Gitee Go 云端构建受免费额度限制且 mobile 包易拖垮全量 build；改为 **push → Webhook → 服务器本地增量构建**，与 G8 的 PM2/Docker 体系衔接。

### 思考过程

1. **构建放哪？** 服务器 2G 轻量机已能跑 `deploy:server --use-tsx`；在服务器 `pnpm build:pc/web` 比 Gitee Go 省额度、环境一致。  
2. **Webhook 与 API 同进程？** 否。发版会 reload PM2，Webhook 监听独立 `:9090` + systemd，避免「发版把自己发死」。  
3. **每次都全量 build？** 否。`detect-deploy-targets.mjs` 按 git diff 路径映射 `server/pc/web`；仅 `docs/` 跳过；`shared` 变更触发三端。  
4. **小程序/H5 呢？** 不走服务器静态发版，仍本地 build + 微信上传（与 §6 发版流程一致）。

### 最终方案

- **日常**：`git push origin main` → Gitee POST → Nginx → `gitee-webhook-deploy.sh` → `pnpm deploy:release --target=...`  
- **强制范围**：提交信息 `[deploy:web]` / `[deploy:all]` 覆盖路径检测  
- **手动兜底**：SSH 执行 `bash scripts/gitee-webhook-deploy.sh` 或 `pnpm deploy:release`  
- **文档**：专题 [发版流程与CI-CD解析.md](./发版流程与CI-CD解析.md) + [服务端命令手册.md](./服务端命令手册.md)

### 亮点

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **增量发版** | 改 web 只 build web，缩短 2G 机发版时间 |
| 2 | **Webhook 与 API 隔离** | systemd 独立进程，PM2 reload 不影响 Hook 接收 |
| 3 | **文档化决策树** | 404/401/无发版等故障有专门排查章节 |

### 重难点

| # | 重难点 | 思考与解决 |
|---|--------|------------|
| 1 | Nginx 443 缺 webhook include | Gitee 走 HTTPS，必须在 443 `server` 块 include snippet；`verify-webhook-nginx.sh` 自检 |
| 2 | nvm 路径导致 systemd 203 | `install-webhook-service.sh --node $(which node)` 指定绝对路径 |
| 3 | 并发 push 重复发版 | `gitee-webhook-deploy.sh` 内 `flock` 锁 |
