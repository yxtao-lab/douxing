## 2. 工程化（低成本、全栈受益）

| 工具 | 契合点 | 建议 |
|------|--------|------|
| **ESLint + Prettier + `packages/eslint-config`** | 多端 Vue/TS 风格不统一；根 README 已列为待办 | **优先**。`@typescript-eslint` + `eslint-plugin-vue`；根目录 `lint-staged` + Husky 防脏提交 |
| **Vitest** | 目前各包 `lint` 多为 `tsc --noEmit`；`@douxing/shared`、Enricher、i18n key 适合单测 | 先在 shared 与 server 核心 service 起步，不必一次全覆盖 |
| **Turborepo** | 7 个子包 Monorepo；改 shared 后需 rebuild 各端 | 构建缓存 + 任务依赖图；与现有 `scripts/pm.mjs` 可并存 |
| **Gitee Webhook 发版** | push → 服务器 `git pull` + 增量 build | **当前方案**；见 [发版流程与CI-CD解析.md](./发版流程与CI-CD解析.md) |
| **Gitee Go** | `.workflow/` 流水线；需开通 Gitee Go 服务 | PR 门禁 / 云端 CI 日志；发版已改用 Webhook · 见 [deploy-production §10.3](deploy-production.md) |

> 以上不碰业务逻辑，但能立刻提升协作质量与发版信心。详见根 [README.md § monorepo 待补充](../README.md#当前项目里还不是典型-monorepo-的部分)。

## 10. Kafka 说明（与兜行技术栈对照）

**Apache Kafka** 是分布式**消息流平台**（Message Streaming Platform）：多个服务通过「发消息 / 收消息」异步通信，并能将大量消息**可靠持久化、按顺序消费**。

### 10.1 核心能力

| 能力 | 含义 |
|------|------|
| **消息队列** | A 服务处理完后丢一条消息，B 服务异步消费，无需同步等待 |
| **事件流（Event Streaming）** | 将「用户下单」「路线发布」「打卡成功」等视为连续事件流，多个下游各自订阅 |
| **削峰填谷** | 流量尖峰时先写入 Kafka，消费者按处理能力逐步消化 |
| **数据管道** | 业务事件同步至分析库、搜索引擎、运营大屏等（ETL / 实时数仓） |

可理解为一条**高吞吐、可回放、多订阅者**的传送带：生产者写入、消费者读取，消息落盘后可重复消费，进程重启不丢数据。

### 10.2 与兜行现有组件对比

| 组件 | 角色 | 与 Kafka 的关系 |
|------|------|-----------------|
| **MySQL** | 业务主数据（用户、路线、订单） | Kafka **不替代** MySQL；可作为变更事件的传输层 |
| **Redis / BullMQ** | 缓存、任务队列（封面 enrich、日汇总等） | BullMQ 偏**任务型**（重试、定时、少量消费者）；Kafka 偏**事件流**（海量写入、多下游、长期保留） |
| **`analytics_events` 表** | DT1 埋点与分析 | 现阶段够用；事件量极大时可改为「先 Kafka 再落库/入仓」 |
| **RabbitMQ**（未使用） | 传统消息队列 | 路由灵活、体量中等；Kafka 更适合**日志型、高吞吐、可回放**场景 |

### 10.3 典型使用场景（行业参考）

1. **订单 / 支付事件**：支付成功 → 发消息 → 更新订单、发通知、写分析、同步搜索索引  
2. **用户行为埋点（DT3）**：App 大量上报点击/浏览，下游分别做漏斗、留存、实时大屏  
3. **日志聚合**：各服务日志统一进 Kafka，再进 ELK / ClickHouse  
4. **CDC 数据同步**：MySQL 变更 → Kafka → 同步 ES / ClickHouse（与 **DT4** 远期方向相关）

### 10.4 兜行现阶段是否需要 Kafka

**结论：现阶段一般不需要。**

| 因素 | 说明 |
|------|------|
| 架构规模 | Express 单体 + MySQL + Redis 可支撑当前业务量 |
| 已有替代 | 异步任务优先 **BullMQ**（与 ioredis 栈一致）；埋点与分析走 **MySQL + DT3 可选 PostHog** |
| 运维成本 | Kafka 需集群、分区、消费组、监控；生产环境通常至少 3 节点才较稳 |
| 路线图 | [数据中台.md](./数据中台.md) DT1～DT3 用 MySQL 交付；DT4 ClickHouse 升级前不必前置 Kafka |

**更适合考虑 Kafka 的时机**：

- 埋点 / 业务事件达**百万级/天**以上，`analytics_events` 写入成为瓶颈  
- 同一事件需**同时**馈送分析、搜索、推荐、DT5 大屏等多个系统  
- 落地 **DT4 ClickHouse** 或实时流式 ETL 管道  
- 微服务拆分后，服务间解耦通信成为主要矛盾  

**一句话**：Kafka 是「大规模、可回放、多消费者」的**事件总线**；兜行当前用 **BullMQ + MySQL 埋点** 更合适，Kafka 属于数据量与架构复杂度上升后的升级选项。

## 12. 一句话总结

项目并非「缺工具」，而是 **工程化、可观测、AI trace、异步任务** 四块仍有空白。最契合当前阶段的组合：

**ESLint + Vitest + Sentry + BullMQ + Langfuse + sharp**

- 前四项：立刻提升开发/运维质量  
- Langfuse：服务 AI 主链与 H3 记忆分析  
- sharp：直接增强已交付的旅程相册（J 线）

落地某一类工具时，请在 [开发记录-重难点与亮点.md](./开发记录-重难点与亮点.md) 或 ROADMAP 对应条目补充验收说明。
