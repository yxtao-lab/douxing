## 2. 兜行数据中台是什么

兜行数据中台是介于 **业务系统（MySQL + API）** 与 **管理端 / 运营决策** 之间的 **轻量数据能力层**，不是独立的大数据平台或实时流计算集群。

```text
业务表（users / routes / orders / check_ins …）
        ↓ 聚合 / 埋点 / 汇总
指标与服务层（/api/analytics/* · analytics.service）
        ↓
管理端展示（工作台卡片 · 数据分析看板 ECharts 折线图）
```

### 2.1 三大目标

| 目标 | 说明 |
|------|------|
| **统一指标口径** | 用户、路线、订单、打卡、规划会话等 KPI 一处定义、多处复用 |
| **可观测** | 总量、趋势、城市排行、（远期）行为漏斗与留存 |
| **可扩展** | 先 MySQL，再日汇总、埋点、ClickHouse；**不推翻 API 契约** |

### 2.2 管理端入口

| 入口 | 路径 | 用途 |
|------|------|------|
| 工作台 | `/` | 路线、订单、打卡等概览卡片，快速扫一眼 |
| 数据分析 | `/analytics` | 侧栏 **数据中台 → 数据分析**；概览、ECharts 趋势折线图、明细表、城市 Top10 |

## 3. 兜行场景下的作用与价值

### 3.1 对角色

| 角色 | 典型场景 |
|------|----------|
| **管理员 / 运营** | 用户与订单是否增长；打卡是否活跃；哪些城市热度高 |
| **产品** | 对比 7/30/90 天趋势；评估功能上线效果（DT3 后可看漏斗与留存） |
| **研发** | 指标逻辑集中在 `analytics.service`；业务表变更时改一处即可 |

### 3.2 与「各业务页自己算数」的对比

| 方式 | 问题 |
|------|------|
| 各模块直连业务表、各自 SQL | 口径不一致、重复开发、难以做跨域趋势 |
| **数据中台** | 统一 API + 统一口径 + 专用看板，管理端与后续埋点共用 |

### 3.3 当前已具备（DT1）

- `GET /api/analytics/overview` — 核心指标总量与近 7 日新增  
- `GET /api/analytics/trends` — 按日趋势（1～90 天）  
- `GET /api/analytics/top-cities` — 打卡城市 Top N  
- `analytics_events` 埋点表（**DT3** mobile/pc 客户端上报 + 服务端写入）  
- Web 管理端 **数据分析** 页：统计卡片 + **ECharts 多指标折线图** + 趋势明细表

## 4. 市面数据中台：价值与常见功能

### 4.1 行业定义

**数据中台** 是企业将分散在各业务系统中的数据，通过 **采集、治理、建模、服务化**，支撑报表、分析、算法与业务复用的 **共享数据能力层**。

核心价值：**算数、取数、用数在一处定义，全组织复用**。

### 4.2 六大价值（行业共识）

1. **统一口径** — 同一指标（DAU、GMV、转化率）有官方定义，避免「数对不上」  
2. **打破孤岛** — 用户、订单、行为、商品可关联分析  
3. **提升决策效率** — 自助看板、固定报表、告警，减少「找 IT 导 Excel」  
4. **复用能力** — 指标、标签、API 建一次，多端复用  
5. **支撑智能化** — 推荐、风控、营销依赖稳定特征与标签  
6. **合规与安全** — 脱敏、权限、审计  

### 4.3 常见功能模块

| 模块 | 做什么 |
|------|--------|
| 数据采集 / 集成 | 库表同步、日志、埋点、API；批处理 + 实时流 |
| 数据存储 / 湖仓 | 数据湖、数仓、OLAP、对象存储 |
| 数据治理 | 元数据、血缘、质量、主数据 |
| 数据开发 / ETL | 调度、分层建模（ODS → DWD → DWS → ADS） |
| 指标管理 | 原子/派生指标、维度、口径文档 |
| 标签 / 画像 | 用户分群、RFM、行为标签 |
| BI / 可视化 | 报表、大屏、自助分析 |
| 数据服务 API | 指标/标签封装为 API |
| 埋点 / 行为分析 | 漏斗、留存、路径 |
| 权限与安全 | 行列级权限、脱敏、审计 |

### 4.4 市面常见形态（举例）

| 类型 | 代表 |
|------|------|
| 国内平台化 | 阿里云 DataWorks + MaxCompute、腾讯云 WeData、华为 FusionInsight |
| 国际现代数据栈 | Databricks、Snowflake、dbt + Airflow + BI 工具 |
| 轻量 / 中小企业 | FineBI、观远、神策、GrowingIO（偏看板 + 埋点 + 行为分析） |

### 4.5 什么规模值得上「完整中台」

| 阶段 | 典型做法 |
|------|----------|
| 初创 / MVP | 业务库 + 聚合 API + 管理端看板（**兜行 DT1**） |
| 成长期 | 埋点、日汇总、OLAP、固定报表（**DT2～DT3 已完成**） |
| 规模化 | 独立数仓、指标平台、标签、实时链路 |
| 大型集团 | 全栈：治理、主数据、多域模型、数据服务化 |

完整中台投入大；团队小、数据源少时，**轻量指标层 + 看板 + 埋点** 往往更划算。兜行采用 **渐进式 DT 路线**，与上述路径一致。

## 5. DT1～DT5 与行业能力对照

### 5.1 总览

| 兜行阶段 | 状态 | 行业里通常叫什么 | 解决的核心问题 |
|---------|------|----------------|---------------|
| **DT1** | 已完成 | 指标 API + 轻量 BI 看板 | 能看数、口径统一 |
| **DT2** | 已完成 | 离线汇总 / T+1 数仓 DWS 层 | 数据多了查询仍快 |
| **DT3** | 已完成 | 埋点平台 + 行为分析 | 知道用户「做了什么」 |
| **DT4** | 未开始 | OLAP 分析库 / 湖仓查询层 | 复杂分析、大数据量秒级 |
| **DT5** | 未开始 | 运营大屏 / 数据驾驶舱 / 空间 BI | 全站旅行分布、用户路径漏斗、投屏决策；见 [数据中台 §9](./数据中台.md#9-dt5-旅行运营大屏规划) |

### 5.2 DT1：指标 API + 埋点表 + 管理端看板

**兜行交付**

- `analytics_events` 表  
- `GET /analytics/overview` · `/trends` · `/top-cities`  
- Web「数据分析」页：侧栏 **数据中台** 分组 · ECharts 五指标折线图 · 趋势明细表 · 城市 Top10  

**对应行业能力**

| 行业模块 | 对应关系 |
|---------|----------|
| 指标 API / 数据服务 | 将 KPI 封装为 HTTP API，供看板与第三方调用 |
| 轻量 BI | 固定看板 + 趋势图，非自助拖拽 BI |
| 业务库实时聚合 | 直接从 OLTP 表 SQL 聚合，适合数据量较小阶段 |

**验收**：管理员登录后可看 30 日趋势与城市排行（**G4** 与 DT1 已于 2026-06-09 合并验收）。

---

### 5.3 DT2：日汇总与定时任务

**兜行交付（已完成 · 2026-06-26）**

- `analytics_daily_metrics` 日汇总表  
- `pnpm analytics:rollup` 每日跑批（CLI + 进程内 2:00 定时）  
- 趋势 API 优先读汇总表；当天实时聚合；未回填回退 DT1  
- 验收：`dt2:analytics-cases`

**对应行业能力**

| 行业模块 | 说明 |
|---------|------|
| 离线 ETL / 批处理调度 | 类似 Airflow、DataWorks 定时任务 |
| 数仓分层 · DWS / ADS | 明细在 ODS/DWD，汇总在 DWS，看板读 ADS |
| 预聚合 / 物化视图 | ClickHouse MV、StarRocks 物化视图等同理 |
| T+1 指标 | 不要求秒级实时，但要稳定、低成本 |

**还不等于**：完整实时数仓、复杂跨域宽表建模。

**价值**：从「能看数」升级为 **数据量增长后仍快、成本低**。

---

### 5.4 DT3：客户端埋点 SDK

**兜行交付（已完成 · 2026-06-26）**

- mobile / pc `trackAnalytics` → `POST /analytics/events`（白名单 + 批量）  
- `GET /analytics/funnel` 旅程漏斗；Web 看板漏斗表  
- 复用 DT1 的 `analytics_events` 与事件模型  
- 验收：`dt3:analytics-cases`

**对应行业能力**

| 行业模块 | 说明 |
|---------|------|
| 埋点采集 / SDK | 神策、GrowingIO、Firebase Analytics 等 |
| 事件模型 | event_name、properties、user_id、session_id、occurred_at |
| 行为分析 / 产品分析 | 漏斗、留存、路径、转化率 |
| CDP 行为层（子集） | 非完整客户数据平台，但有行为事件流 |

**还不等于**：完整标签/画像平台、实时推荐特征、营销自动化圈人。

**价值**：从 **结果指标**（多少订单）到 **过程指标**（哪一步流失、功能是否被使用）。

---

### 5.5 DT4：分析库升级（MySQL → ClickHouse）

**兜行交付（规划）**

- 业务仍写 MySQL，分析侧同步 ClickHouse  
- 复杂 OLAP、多维分析  
- **`/api/analytics/*` 契约不变**，仅内部换查询引擎  

**对应行业能力**

| 行业模块 | 说明 |
|---------|------|
| OLAP 引擎 | ClickHouse、StarRocks、Doris、BigQuery 等 |
| 读写分离 / 分析库 | OLTP 与 OLAP 分离，互不影响 |
| CDC / ETL 同步 | Canal、Debezium 等将变更同步到分析库 |
| 多维 / 即席查询 | 大时间跨度、细粒度、多维度 TopN |

**还不等于**：Flink 实时流、完整数据治理平台、集团级指标管理平台。

**价值**：支撑 **更长时间、更细粒度、更复杂维度** 的分析，对齐《详细设计文档》「数据分析服务 + ClickHouse」。

## 6. 四阶段在行业数据栈中的位置

```text
行业完整数据中台（简化）

  采集层 ──→ 存储层 ──→ 治理层 ──→ 建模/ETL ──→ 指标/标签 ──→ BI/API ──→ 算法
     │           │           │            │              │           │
  DT3 埋点    DT1 业务表   （暂无）      DT2 日汇总      DT1 指标    DT1 看板
     │           │                        │              │           │
     └───────────┴────────────────────────┴──────────────┴── DT4 OLAP 升级
```

| 行业层级 | DT1 | DT2 | DT3 | DT4 |
|---------|-----|-----|-----|-----|
| 采集 | 服务端可写事件 | — | 客户端埋点 | CDC 同步 |
| 存储 | MySQL 业务表 + events | + 日汇总表 | 事件量增大 | + ClickHouse |
| ETL / 调度 | 实时 SQL 聚合 | 日跑批 rollup | 事件入库管道 | 同步 + 复杂聚合 |
| 指标 | 核心 KPI 口径 | 趋势走汇总 | 漏斗 / 留存 | 多维 OLAP |
| 消费 | 管理端看板 | 同上，更快 | 产品 / 运营行为分析 | 复杂报表 |

## 7. 能力边界：DT4 之后仍不包含什么

做到 **DT4** 后，兜行具备行业里 **「轻量～中型产品数据平台」** 的主干能力，通常仍 **不包含**：

- 主数据管理（MDM）  
- 全链路数据血缘与质量平台  
- 独立指标平台（指标版本、审批、血缘）  
- 标签引擎 + 营销圈人  
- 实时 Flink 流 + 实时大屏  
- 跨 BU 多租户数据域治理  

对 **出行 / 路线 / 打卡 / AI 规划** 场景，DT1→DT4 已可覆盖：运营看大盘（DT1/DT2）、产品看行为（DT3）、数据变大后深分析（DT4）。

## 8. 实施优先级建议

推荐顺序与 [数据中台.md](./数据中台.md) 一致：

```text
DT1（已完成）→ DT3（已完成）→ DT2（已完成）→ DT5（按需）→ DT4（按需）
```

| 顺序 | 理由 |
|------|------|
| ~~DT2~~ | ✅ 趋势查询已走 T+1 汇总层 |
| ~~DT3~~ | ✅ 行为漏斗已可用 |
| **DT5** | 需投屏运营决策时启动 |
| **DT4** | MySQL 聚合或明细扫描成为瓶颈时再上 ClickHouse |

## 9. 一句话总结

| 阶段 | 兜行 | 行业一句话 |
|------|------|-----------|
| DT1 | 能看统一口径的趋势与排行 | 指标 API + 轻量 BI |
| DT2 | 百万级行趋势仍秒开 | T+1 汇总层 + 调度 |
| DT3 | 知道用户在 App 里做了什么 | 埋点 + 行为分析 |
| DT4 | 复杂多维 OLAP | 分析库 / Lakehouse 查询层 |

**整体**：兜行数据中台是 **「T+1 指标 + 产品分析 + OLAP」的精简版**，思路与行业一致，体量适配当前 Monorepo 规模，随 ROADMAP **DT** 阶段逐步演进。
